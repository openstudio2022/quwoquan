# 全局产品概念基线

> 适用阶段：`/explore`、`/prd`、`/design`、`/baseline`
>
> 文档目的：在进入各域 PRD 之前，先冻结全 App 的核心对象、关系模型、品牌解释与页面层级，避免同一概念在不同文档、不同页面、不同服务中被重复发明。

---

## 1. 文档定位

本文件定义趣我圈在产品层面的世界观、核心对象与跨域关系，不直接替代：

- metadata 中的 `route / surface / operation / field`
- 各 `L1/L2/L3` 节点的场景行为规格
- 云侧 DDD 与服务分层文档

本文件回答的问题是：

- 用户到底在 App 里会看到哪些核心对象
- 这些对象之间是什么关系
- 整个 App 的品牌、AI、内容、关系、搜索和主页应该如何统一解释
- 后续 `/prd` 应该沿着哪套概念骨架继续展开

本文件与 `00_GLOBAL_TERMINOLOGY.md` 的分工如下：

- `00_PRODUCT_CONCEPT_SYSTEM.md`：定义“有什么、怎么关联、各域分别扮演什么角色”
- `00_GLOBAL_TERMINOLOGY.md`：定义“这些东西应该怎么命名、哪些词禁止前台使用、旧词怎么迁移”

两份文档不建议硬合并：

- 本文件更像“世界观和对象地图”
- 术语表更像“命名规则和迁移字典”

## 2. 品牌定位与产品主张

### 2.1 品牌名

- 品牌名：`趣我圈`
- AI 助手名：`小趣`

### 2.2 产品定位

趣我圈不是单纯的兴趣论坛，也不是单纯的黄页目录，更不是只有聊天的 IM。

当前统一定位为：

**一个以 `交集` 为连接主线、以 `小趣` 为引擎、以可信主页承接真实生活信息的 AI Native 同趣社区。**

北极星：`交集`。差异化引擎三角：`小趣 × 实时推荐 × 交集`。

主 slogan：

**遇见同趣，绽放热爱。**

首屏利益话：

**看见你和同学、和远方的交集。**

解释语：

**小趣主动为你筛选、撮合、规划——专注你的热爱，剩下的交给我。**

### 2.3 品牌解释

`趣我圈` 中的“圈”是品牌解释，不等于任何单一产品入口词。它代表的是：

- 与我有关的人
- 与我有关的群
- 与我有关的生活、地点、物和组织
- 以及我和它们之间的 `交集`

因此：

- 品牌层保留 `趣我圈`
- `圈子` 收敛为兴趣型可加入对象（如 `摄影圈`、`露营圈`），不再作为承接实体主页索引、组织与全局关系沉淀的总入口词
- 组织（`学校 / 院系 / 班级 / 公司 / 部门`）、地点和事物、人各自用对象名直接呈现，不套“圈子”
- 全 App 的连接主线是 `交集`：每个对象页、推荐位、内容卡都解释“你和它的交集”
- 底栏一级入口的名称与承载属于 IA 决策，由后续首页/圈子会话与 `circle-community` 域统一定夺（见第 19 节受影响域标注）

### 2.4 主张

建议统一沿用这条产品主张作为解释口径：

**遇见同趣，绽放热爱。**

> 升级说明：原表达「同趣相连，世界更近」偏静态连接语义；当前主 slogan 保留「遇见同趣」的主动撮合瞬间感，并以「绽放热爱」承接花瓣品牌视觉与用户热爱被看见、被点亮的情绪价值；解释语同步切换为小趣第一人称承诺口吻。

### 2.5 交集（北极星）

`交集` 是全 App 的核心记忆点、北极星指标与首发收敛主线。

定义：交集 = 你和某个对象之间，客观存在、可逐条枚举、每条可解释来源、并能直接驱动下一步动作的共同连接点。必须同时满足四条件，缺一条就退化成普通“猜你喜欢”：

- 客观可证：如“都去过故宫”“都是北大 2020 级”“都收藏了这篇川西攻略”。
- 可枚举：`128 个交集点` 必须能点开看到这 128 条。
- 可解释：每条都有来源（同校 / 同去过 / 同圈子 / 同收藏 / 共同关注）。
- 可行动：看到交集后能立刻关注、打招呼、进同一个圈子、约一起出行。

五类交集来源：`身份 / 地点 / 内容 / 关系 / 兴趣`。

交集是一层贯穿全 App 的“连接解释层”，不是单独页面：它出现在首页 `今日交集`、对象页交集卡、内容卡交集线索，统一消费同一套结构化 `交集理由`（端只展示、不本地拼装文案）。交集的标签锚点统一使用路径制 `tagRef`（见第 18 节标签体系）。

完整的交集词典、七个母表达边界、关系语言规则、细 `kind/sourceRef`、桥接型交集、影响词典与 legacy alias 迁移规则，统一下钻到 `specs/product/intersection-definition-and-application.md`。

### 2.6 差异化引擎三角：小趣 × 实时推荐 × 交集

- 实时推荐：算得准（召回 + 排序，已有能力）。
- 交集：解释得清（统一标签图谱上的可解释重合 + 社交关系边）。
- 小趣：说得明并撮合行动（生成解释、引导关注/加入/打招呼/约出行）。

三者闭环：推荐排序 → 交集理由 → 小趣解释 → 用户行动 → 行为回流推荐。这是微信（有关系、无兴趣公开图谱）与小红书（有内容、无你的真实关系）结构上都给不了的差异点。

## 3. 全 App 领域与业务对象地图

| L1 能力域 | 产品层角色 | 核心业务对象 | 用户前台主要感知 |
|---|---|---|---|
| `discovery-content` | 负责发现、分发、互动与反馈 | Feed、Post、Comment、互动/负反馈、媒体与发布链路 | 发现流、内容、评论、互动、发布 |
| `circle-community` | 负责同趣入口、关系沉淀与关系主页治理 | 圈子、组织主页、群、成员、群级协作 | 圈子、学校/公司/班级、公共群、自建群 |
| `chat-conversation` | 负责实时沟通与消息同步 | Conversation、Message、Inbox、ConversationMember、ConversationUserState | 消息、会话、聊天记录、@小趣回复 |
| `user-identity-profile-relationship` | 负责主体身份、关系与个人主页世界观 | OwnerAccount、SubAccount、Profile、ContactDiscovery、Invite Attribution | 身份、个人主页、联系人、切换身份 |
| `assistant-run-learning` | 负责助手运行、反馈与学习闭环 | Run、Stream、策略模板、学习事件、画像提案 | 小趣、助手回复、反馈 |
| `global-search-experience` | 负责跨域搜索壳层与结果编排 | 全屏搜索、记录、联想、网络结果页、小趣搜、圈子结果 | 搜索、最近在搜、圈子结果、联系人结果、小趣搜 |
| `shared-homepage-network` | 负责具体事物主页、口碑、认领与下线 | EntityProfile、ReviewTemplate、ClaimRequest、SourceEvidence、StatusReport | 车型主页、酒店主页、景点主页、餐厅主页、口碑 |
| `product-ops-growth` | 负责增长、运营与效果闭环 | 运营事件、增长策略、实验与观测 | 一般不直接作为前台对象出现 |
| `platform-ops-governance / gateway / runtime` | 负责基础设施与治理 | 配置、可观测、流量治理、运行时能力 | 不直接作为前台对象出现 |

结论：

- 用户前台真正会感知的对象，不止 `共享主页 / 圈子 / 群 / 内容`
- 还包括 `身份/个人主页`、`会话/消息`、`小趣`、`搜索`
- `发现` 与 `搜索` 是横切层，不是孤立业务对象，但会强烈影响用户对全 App 的理解

## 4. 产品总模型

### 4.1 用户语言对象（前台只用这些）

趣我圈前台只用用户能听懂的自然对象，不向用户暴露 `个人主页 / 共享主页 / 关系主页` 这类工程抽象：

1. `人`：我、TA、作者、联系人。前台用 `我的主页 / TA的主页 / 作者主页`，不说“个人主页”；`联系人` 是消息和搜索里的聚合视图，不是关系等级。
2. `地点和事物`：具体对象名 + 类型标签（`学校 / 景点 / 餐厅 / 酒店 / 车型`），不说“实体 / 共享主页”。
3. `圈子`：兴趣型可加入对象（摄影圈、露营圈），不作全局总称。
4. `组织`：`学校 / 院系 / 班级 / 社团 / 协会 / 公司 / 部门`，前台用具体名。
5. `群`：`群 / 公共群 / 自建群`。
6. `内容`：`笔记 / 作品 / 提问 / 口碑`（内容类型）叠加 `图文 / 视频 / 文章`（表达形式）。
7. `会话`：用户与用户、用户与群、用户与小趣的实时沟通上下文。

横切：`身份` 决定“谁在使用”；`交集` 是贯穿全 App 的连接解释层；`小趣` 是连接与撮合引擎；`首页` 与 `搜索` 是分发与查找横切层。

> 工程分层说明（不进前台）：内部仍可按 `个人主页 / 共享主页 / 关系主页` 做能力分层，但它们只是工程抽象，前台一律用上面的自然对象名。`共享主页` 对应“地点和事物”，`关系主页（兴趣型 / 组织型）` 对应“圈子 / 组织”。

### 4.2 三条横切能力

除上述对象外，全 App 还有三条横切能力：

- `首页`：把关注对象动态与精品内容推荐到用户面前
- `搜索`：让用户跨域查找内容、人、会话、圈子与后续主页
- `小趣`：与搜索合并为全局入口，贯穿内容、搜索、会话、评论与关系沉淀的 AI 连接层

### 4.3 一句话总纲

**身份决定“谁在使用”；关注解释“我是否主动连接 TA”；人 / 地点和事物 / 圈子 / 组织 的主页回答“这是谁、这是什么”；圈子、组织和群沉淀共同参与；内容负责表达；会话负责实时沟通；交集解释“你和它的连接”；小趣据交集撮合行动。**

## 5. 身份与主体

### 5.1 基本原则

- `OwnerAccount / 主控账号` 负责登录、安全、恢复、设备与通讯录发现。
- `SubAccount / 子账号` 是应用内真实使用主体，承载主页、圈子、内容、会话、邀请与关系。
- 前台默认不把 `OwnerAccount` 暴露成用户心智中心。
- 用户前台默认理解的是“身份”，不是“主控账号”。

### 5.2 个人主页

个人主页属于 `SubAccount`，承载：

- 公开身份与资料
- 发布过的内容
- 关系与被关注状态
- 在圈子和会话里的活跃痕迹

### 5.3 归属原则

- 通讯录发现归 `OwnerAccount`
- 关注、圈子、群、会话、内容、邀请归因归 `SubAccount`
- 子账号切换必须对圈子、聊天、助手、推荐、通知上下文立即生效

## 6. 主页体系

### 6.1 主页是总称；前台用对象名，三类抽象仅内部分层

“主页”是一个总称。**前台不向用户暴露 `个人主页 / 共享主页 / 关系主页` 这三个词**，用户看到的是自然对象名：

- `人` → `我的主页 / TA的主页 / 作者主页`
- `地点和事物` → 对象名 + 类型标签（`学校 / 景点 / 餐厅 / 酒店 / 车型`）
- `圈子` → 兴趣型对象名（摄影圈）
- `组织` → 具体组织名（复旦大学 / 推荐算法部）

`个人主页 / 共享主页 / 关系主页` 仅作为内部工程能力分层保留（§6.2–§6.4 是内部分层描述）。后续 PRD 写“主页”时必须写清是哪类对象，并在前台落地为对象名而非抽象词。

### 6.2 个人主页

个人主页围绕 `SubAccount` 建立，是“谁”的页面。

它解决：

- 身份展示
- 内容展示
- 关系展示
- 个人经营

### 6.3 共享主页

共享主页围绕具体事物建立，是“这是什么”的页面。

baseline 阶段优先支持：

- `车型`
- `酒店 / 民宿`
- `餐厅`
- `景点`

共享主页至少承接：

- 基础信息
- 口碑
- 内容
- 提问
- 相关群组
- 官方/服务信息

共享主页原则：

- 口碑依附于共享主页，不单独漂浮存在
- 内容可以挂载共享主页
- 群组可以关联共享主页
- 共享主页可以推荐相关群组
- 用户补充一个主页，不等于拥有它

### 6.4 关系主页

关系主页围绕“人为什么在一起”建立，是“谁围绕它沉淀关系”的页面。

关系主页分两种模板：

- 兴趣型：`圈子`
- 组织型：`学校 / 院系 / 班级 / 公司 / 部门`

关系主页可以关联一个共享主页，但不等于共享主页本身。

## 7. 圈子与关系主页

### 7.1 圈子是兴趣型对象，不是全局总入口

`圈子` 收敛为**兴趣型可加入对象**（摄影圈、露营圈、车友圈），表示“同趣的人聚在一起”的地方。它**不再**作为承接组织、地点和事物、全局关系沉淀的总称。

- 组织（学校 / 院系 / 班级 / 公司 / 部门）用 §7.3 组织对象表达，不叫圈子。
- 地点和事物用具体对象页表达（见第 6 节、`shared-homepage-network`），不叫圈子。
- 底栏一级入口的名称与承载是 IA 决策，由后续首页 / 圈子会话与 `circle-community` 域统一定夺（见第 19 节）。上下文不清时写清“圈子（兴趣型对象）”。

### 7.2 兴趣型关系主页

前台名称：

- `圈子`

示例：

- `摄影圈`
- `L9车友圈`
- `露营圈`

角色：

- `圈主`
- `圈管`

### 7.3 组织型关系主页

前台直接显示具体组织或节点名，不再硬套“圈子”。

示例：

- `复旦大学`
- `计算机学院`
- `2020级3班`
- `字节跳动`
- `推荐算法部`

角色：

- `负责人`
- `管理员`

### 7.4 统一原则

- `圈子` 从全局总称降级为兴趣型关系主页的一种类型名
- 组织型主页不再使用“圈主”一类兴趣社区词
- 学校 / 公司在 baseline 阶段优先作为组织型关系主页，而不是共享主页标准类目

### 7.5 组织型主页与共享主页的映射

学校、院系、班级、公司、部门等需要成员治理、群层级和会话承接的对象，产品真相源归 `circle-community` 的组织型关系主页：

- `学校 / 公司`：`Circle.kind = organization`，前台显示具体名称，不套“圈子”。
- `院系 / 班级 / 部门 / 团队`：作为组织型关系主页下的 `CircleGroup(groupType = org_node)` 子节点表达。
- `班级群`：不是新的会话类型，而是 `CircleGroup(nodeType = classroom)` 绑定一个 `Conversation(type = group)`。
- 共享主页中的 `HomepageType.university` 仅用于百科式信息、口碑、内容挂载或外部对象索引；若需要加入、成员、班级、群治理，必须通过 `Circle.linkedHomepageId` 关联到组织型关系主页。

因此“学校实体下建班级群”的用户语言落地为：学校组织主页 → 院系/年级/班级节点 → 班级群会话。共享主页只能推荐或挂载相关群组，不拥有群与会话治理。

## 8. 群

### 8.1 定义

群是关系主页内的子单元。

群不是聊天的同义词。聊天只是群的一种能力。

群可以承接：

- `交流`
- `资料`
- `公告`
- `活动`
- 小范围成员协作

### 8.2 群类型

baseline 统一为：

- `公共群`
- `自建群`

但在组织型关系主页中，前台优先显示具体节点名，不强行露出“群”字。

例如：

- `2020级3班`
- `推荐算法部`
- `摄影小组`

底层仍可复用统一的群能力。

### 8.3 群与会话的关系

- 群是成员和协作单元
- 会话是实时沟通单元
- 一个群通常会有自己的主会话或交流能力
- 但“群”不等于“会话”
- 群通过 `CircleGroup.conversationId` 绑定主会话；会话通过 `circleGroupId` 回指群单元
- `Conversation.type = group` 是群会话的统一主语义；不得新增 `temporary_group`、`circle_conversation`、`homepage_conversation` 等并列会话类型
- 临时群、自建群、班级群、圈子默认群的差异属于来源、绑定对象和生命周期策略，不属于新的会话顶级类型

### 8.4 baseline 规则

- 小圈子或小组织可只有一个公共群
- 大型关系主页可有多个公共群
- 用户可加入多个自建群
- 群不承担全局公开内容的主分发职责

## 9. 内容

### 9.1 用户动作

全局统一动作叫：

- `发布`

不再把所有内容动作都粗暴统一成“发帖”。

### 9.2 一级内容类型

一级内容类型冻结为：

- `笔记`
- `作品`
- `提问`
- `口碑`

### 9.3 表达形式

内容编辑入口继续保留自然创作心智：

- `图文`
- `视频`
- `文章`

这里区分两层：

- `内容类型`：这条内容是什么
- `表达形式`：用户用什么方式开始创作

### 9.4 与发现域的映射

`discovery-content` 规格里仍有 `文章 / 微趣 / 美图 / 视频` 这类展示或投影分组。  
全局概念层统一解释为：

- `笔记 / 作品 / 提问 / 口碑` 是业务内容类型
- `文章 / 微趣 / 美图 / 视频` 是发现流、媒体投影或展示家族

后续 PRD 不得把两层概念混成一层。

### 9.5 与主页和圈子的关系

- `口碑` 必须绑定一个共享主页
- `笔记 / 作品 / 提问` 可选择绑定共享主页
- 内容可以发布到个人，也可以发布到圈子或关系主页
- 从圈子内发内容时，当前关系主页默认已选中
- 从全局发布入口发内容时，可在发布页补选共享主页和关系主页
- 群层不作为公开内容主时间线

### 9.6 互动与反馈

内容默认承接：

- 评论
- 点赞
- 收藏
- 转发
- 负反馈
- 举报

这些属于 `discovery-content` 与 `product-ops` 的共用反馈基线。

## 10. 会话与消息

### 10.1 定义

会话是实时沟通上下文，属于 `chat-conversation` 域。

用户前台主要感知为：

- `消息`
- `会话`
- `消息`
- `聊天记录`
- `收件箱 / 会话列表`

### 10.2 类型

- `1v1 会话`
- `群会话`
- `圈子 / 群关联会话`

内部模型冻结为：

- `direct`：1v1 正式会话。
- `group`：所有群会话的主类型，包括临时群、自建群、圈子默认群、圈子自建群、组织节点群、班级群和主页相关群入口落到的群会话。
- `encrypted`：加密或密信类能力的保留类型；未接入 chat-service 主链前不得作为商用主推入口。

既往 `circle` 会话输入与存量记录只能按 `group` 主语义解释，不得作为新的前台会话类型继续扩张。

### 10.3 与圈子的边界

- 圈子负责关系沉淀
- 群负责小范围协作
- 会话负责实时沟通
- 群和会话常常绑定，但不是同一层对象

## 11. 小趣与助手

### 11.1 用户前台对象

用户前台感知到的助手对象主要有：

- `小趣`
- `小趣搜`

### 11.2 产品角色

小趣不是一个孤立功能，而是贯穿全 App 的连接层：

- 在搜索里：以 `小趣搜` 结果页出现
- 在会话里：以 `ConversationMember.memberType = assistant` 作为助手成员参与 1v1 或群会话
- 在内容与主页里：提供理解、建议与后续学习闭环
- 在资料与画像里：输出提案，但不绕过治理规则直接改事实主档

会话内小趣的商用口径：

- 小趣不是新的会话类型，也不是独立“机器人聊天”并列入口。
- 用户可在会话内邀请小趣，并通过 `@小趣` 触发助手回复。
- 小趣发言必须落为 `Message.type = assistant_reply`，进入同一消息流、同一同步与审计链路。
- 私人助手全屏会话保留深度任务场景；会话内小趣复用同一助手 runtime，不维护第二套助手逻辑。

### 11.3 内部抽象

内部继续使用：

- `Run / Stream`
- 策略模板
- 学习事件
- 反馈注入
- 画像提案

这些是内部能力名，不作为前台主词。

## 12. 搜索与发现

### 12.1 发现

发现不是单独对象，而是把内容、主页、群组和关系推荐到用户面前的横切能力。

发现域负责：

- 发现流
- 推荐排序
- 内容反馈
- 运营与评估数据回流

### 12.2 搜索

搜索是跨域壳层能力，不是单独业务主对象。

当前基线下，全局搜索优先覆盖：

- 内容
- 联系人
- 聊天记录
- 群组
- 小趣搜

共享主页搜索在 `shared-homepage-network` 中单独定义，并在后续与全局搜索进一步收口。

### 12.3 统一原则

- 发现负责“把什么推给你”
- 搜索负责“让你主动找到什么”
- 两者都不能发明第二套对象命名

## 16. baseline 范围冻结

在本概念基线下，baseline 阶段冻结如下：

- 北极星：冻结 `交集`（四条件 / 五来源）与差异化引擎三角 `小趣 × 实时推荐 × 交集`

- 标签：冻结路径制 taxonomy（`publish/v1/tags`）为唯一标签真相源，废弃扁平 `tag_taxonomy.yaml`
- 身份：冻结 `OwnerAccount / SubAccount` 双层主体边界

- 圈子：冻结为兴趣型可加入对象，不作全局总称；组织用具体名表达
- 群：冻结为 `公共群 / 自建群`
- 内容：冻结为 `笔记 / 作品 / 提问 / 口碑`（内容类型）叠加 `图文 / 视频 / 文章`（表达形式）
- 会话：冻结 `会话 / 消息 / 会话列表` 的全局定义；群会话统一按 `group` 主语义解释，`circle` 不再作为前台会话类型扩张
- 社交关系：冻结唯一关系概念为 `关注`；`互相关注` 只是两条关注边同时存在的派生状态；`拉黑` 是门禁，`打招呼 / 私信 / 会话` 是消息流程，`联系人` 是消息与搜索的聚合视图。不得新增或保留好友、同好、密友、挚友等关系等级。

- 搜索与发现：冻结“发现是横切推荐层、搜索是横切查找层”的定位

- 学校 / 公司的复杂组织树治理细节

## 18. 标签体系（交集与对象的统一底座）

### 18.1 唯一标签真相源

全 App 的标签唯一真相源是数据工程汇总的**路径制 taxonomy**（`quwoquan_data/publish/v1/tags/`）：

- 四分组 `Topic / Audience / Format / Entity`，`tagId = 目录路径`（如 `Entity/机构/学校/北京大学`、`Topic/地理/中国/四川省/成都市`、`Topic/旅行/自驾`）。
- 含层级（父子 = 目录）、别名 `aliases`、来源 `sourceRefs`、共现图谱与反向索引。
- 实体、内容、圈子、用户、交集统一通过 `tagRef / geoTagRef / entityRef` 引用同一套标签。

### 18.2 废弃扁平 taxonomy

云侧扁平 `tag_taxonomy.yaml`（`topic_travel` 这类扁平 id）这套并行体系**废弃并清理**：`post.tags / circle.tags / entity.categoryTags|highlightTags / 用户兴趣` 统一切到路径制 `tagRef`，禁止再新增第二套标签枚举。过渡期可保留 `旧扁平id → 路径tagRef` 映射用于回填，回填完成即删除。

### 18.3 交集 = 标签图谱重合 + 关系边

- 交集 = 对象在统一标签图谱上的可解释重合（共享 `tagRef / geoTagRef / entityRef`）+ 关注关系边（关注 / 互相关注 / 共同关注）。
- `交集理由` 用 `dimension`（五来源闭集：身份 / 地点 / 内容 / 兴趣 / 关系）+ 开放标签锚点 `tagRefs`（关系维度改挂 `relationRef`），不使用闭集 `reasonType` 枚举。
- “同校 / 同班 / 同公司”不再各占枚举值，而是 identity 维度下不同的 `entity tagRef`；“同城”= 共享 geoTagRef；“兴趣相近”= 共享 `Topic` 垂类 tagRef。taxonomy 扩展自动覆盖，无需改契约，不把兴趣相近命名为关系等级。

## 20. 2026H1 商用定位重构增量（冻结）

> 本节由「产品统一定位与 UX 重构」会话冻结，是 `specs/product/2026H1-positioning-refactor/` 需求包群（WP1–WP8）的概念真相源。与本文件第 2–19 节冲突时，以本节为准；与 metadata 冲突时，以 metadata 为准。

### 20.1 产品核心闭环（统一口径）

```text
发现内容 → 理解实体 → 进入圈子 → 产生交集 → 建立关系 → 参与讨论 → 创作内容 → 影响他人 → 继续被推荐
```

闭环每一环对应可观测事件，是 AppRoot UAT（T4 旅程）的骨架；任何需求包不得只优化单环而切断上下游（如：创作不绑实体/圈子=切断「理解实体→创作」回流）。

### 20.2 实体先行（与既有「共享主页」口径合并）

- 「实体」与「共享主页」是同一能力的两个名字：`实体` 为概念/PRD 词，`共享主页` 为既有 PRD 能力名，前台仍只用对象名（`清华大学`、`九寨沟景区`）+ 类型标签，**前台禁用「实体」一词不变**。
- 实体的产品价值定位从「百科介绍」升级为「连接锚点」：实体主页必须回答 `我与它有什么连接 / 谁也关注它 / 哪些圈子围绕它 / 正在发生什么讨论`。
- 实体主页四件套：`与我的连接`（交集卡）、`认识这个对象`（介绍摘要 + 完整介绍页）、`内容 / 讨论 / 兴趣圈` 三 Tab、上下文创作入口。
- 完整实体介绍页是新增长期页面（承载 800 字以上图文、时间线、相关人物/实体、历史沿革），介绍内容可由数据工程（`qwq-data`）生产供给。
- 实体与圈子为双向关联：实体是客观对象，圈子是兴趣视角；实体页「兴趣圈」Tab 与圈子页关联实体互为入口。

### 20.3 交集：五维闭集 + 七个母表达（高层入口）

- **维度闭集不动**：`identity | location | content | interest | relationship` 五维（metadata `intersection_reason.yaml` 真相源）。
- **用户表达词表**（高层冻结，落在证据组 kind + 云侧 `primaryText` 层，端只读直出、禁止拼装——G2 不变）：

```text
共同关注的人 → relationship / sharedFollowees（legacy alias: mutualFriend；真实第三方共同关注集合，非仅互关）
共同圈子   → relationship / sharedCircle
共同兴趣   → interest     / sharedTagSample（事实级表达，非 affinity 伪装）
共同地点   → location     / coVisitedPlace、followeeVisited、contactVisited
共同校友   → identity     / alumni（首发以「同校」entity tagRef 事实落地，校友图谱后置）
共同收藏   → content      / coFavorited（新增）
共同讨论   → content      / coCommented（新增）
```

- 完整的母表达边界、深层交集词典、关系语言修正与标准名 / legacy alias 迁移规则，详见 `specs/product/intersection-definition-and-application.md`。
- 交集四条件（可证 / 可枚举 / 可解释 / 可行动）扩展适用于**影响数字**：任何「N 人通过 TA 建立新连接」类数字必须可点开枚举来源，无真实归因数据则整行收起，禁止伪造。
- 交集展示结论不展示推导：不堆头像、不暴露算法术语；事实（fact）优先于概率（affinity），affinity 不得伪装事实。

### 20.4 连接 / 影响 / 讨论（用户语言增量）

- `连接`：人与人、人与内容、人与实体、人与圈子的关系总称（模块名：`你们的连接 / 与你的连接 / 我的连接`）。
- `影响`：一个人、圈子或实体帮助他人产生连接的能力（模块名：`TA的影响 / 我的影响力 / 圈子影响`）；数据必须满足 20.3 的四条件。
- `讨论`：实体或圈子下结构化交流分区的用户侧统一名，承接既有 `群` 的前台呈现（详见 `00_GLOBAL_TERMINOLOGY.md` 第 18 节）；讨论详情内承载聊天与内容流，`实体/圈子 → 讨论 → 聊天/内容流` 为标准下钻路径。

### 20.5 四段式主页结构（用户 / 我的 / 实体 / 圈子统一）

```text
头部身份（封面 + 头像 + 名称 + 身份标签单行 + slogan + 操作按钮）
连接模块（纵向列表 ≤3 条 + 查看更多；交集卡同源）
影响 / 介绍模块（用户=影响力卡；圈子=圈子影响；实体=认识这个对象摘要）
Tab 内容区（用户=作品/圈子/互动…；实体=内容/讨论/兴趣圈；圈子=内容/讨论/成员）
```

第一人称页面（我的主页）禁止出现第三人称措辞（`你们的连接 / TA的影响`）。

### 20.6 统一设计原则（视觉层冻结）
