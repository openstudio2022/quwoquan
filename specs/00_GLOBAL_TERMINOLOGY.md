# 全局术语与命名规则

> 适用阶段：`/explore`、`/prd`、`/design`、`/baseline`
>
> 本文档是跨产品、跨端云、跨 feature-tree 的统一术语入口。

---

## 1. 文档目的

本文件用于解决以下问题：

- 同一个概念在不同文档、不同页面、不同服务里被多次命名
- 用户语言、PRD 语言、技术语言没有分层
- 记录设计稿、旧 spec、metadata、代码注释对同一对象使用了不同叫法

本文件不替代 metadata 中的字段、route、surface、operation 定义；
本文件只定义**概念名称、使用边界、优先级和迁移口径**。

与 `00_PRODUCT_CONCEPT_SYSTEM.md` 的分工：

- `00_PRODUCT_CONCEPT_SYSTEM.md` 负责“对象与关系”
- 本文件负责“命名与用词”

两份文档不建议直接合并，因为：

- 概念系统更稳定，更新频率低
- 术语表更偏规则、迁移与纠偏，更新频率高

---

## 2. 优先级规则

后续写 PRD、设计文档、页面文案和服务说明时，统一按下面的优先级执行：

1. `metadata`
仅负责 `path / route / surface / operation / field / enum` 的机器真相源。

2. `00_PRODUCT_CONCEPT_SYSTEM.md + 本术语表`
负责全局产品概念、用户语言、内部抽象词和命名边界。

3. `feature-tree 各 L1/L2/L3 spec`
负责场景行为、流程、验收与页面细节，不得无说明地重新发明全局名词。

4. `记录 openspec / 旧设计文档 / 旧 UI 文案`
仅作背景参考；若与本术语表冲突，以本术语表为准。

## 3. 品牌与产品层术语

| 层级 | 术语 | 是否前台使用 | 定义 | 示例 |
|------|------|-------------|------|------|
| 品牌 | `趣我圈` | 是 | App 母品牌名 | App 名、品牌传播 |
| 产品定位 | `AI Native 同趣社区` | 可用于对外描述 | App 的一句话产品定位 | 应用商店副标题、介绍页 |
| 品牌主张 | `遇见同趣，绽放热爱` | 是 | 全局 slogan，表达"小趣主动撮合同趣的人与圈"，并以"热爱绽放"承接花瓣品牌视觉 | 欢迎页、首页精品首屏、品牌介绍 |
| 兴趣型对象 | `圈子` | 是 | 兴趣型可加入对象（摄影圈、露营圈），不作全局总称 | 圈子详情、兴趣聚合 |
| 北极星 | `交集` | 是 | 你和对象之间客观可证、可枚举、可解释、可行动的共同连接点（四条件 / 五来源） | 今日交集、你们的交集、你和这里的交集 |
| 找同趣入口 | `同趣 / 找同趣 / 兴趣配对` | 是 | 以交集（事实）与亲和力（推荐）为半径，帮用户发现同趣的人 / 圈子 / 地点并行动的发现入口；底栏 `+` 动作面板入口名「兴趣配对」，页面主词「找同趣」，能力短标签「同趣」 | `+` 动作面板「兴趣配对」、找同趣页、兴趣配对结果区 |
| 差异化引擎 | `小趣 × 实时推荐 × 交集` | 否（内部口径） | 推荐算得准 + 交集解释得清 + 小趣说得明并撮合 | 引擎三角说明 |
| AI 助手 | `小趣` | 是 | App 内的统一助手名 | 助手页、会话内 @小趣 |
| 搜索结果页助手入口 | `小趣搜` | 是 | 搜索里的 AI 结果入口 | 网络结果页左侧 tab |

### 使用规则

- `趣我圈` 的“圈”是品牌解释，不等于产品层统一入口词
- `圈子` 收敛为兴趣型对象，不作全局总称；底栏一级入口名称与承载是 IA 决策，由 `circle-community` 与首页/圈子会话定夺
- `交集` 是全局连接解释层，出现在首页、对象页、内容卡，统一消费结构化 `交集理由`，端只展示不拼装
- `找小趣` 不作为底栏频道，而与全局搜索组成一级页顶部的全局入口

## 4. 身份与人

| 层级 | 术语 | 是否前台使用 | 定义 | 示例 |
|------|------|-------------|------|------|
| 用户语言 | `身份` | 是 | 用户在 App 内的真实使用主体心智 | 切换身份 |
| 用户语言 | `我的主页 / TA的主页 / 作者主页` | 是 | 围绕某个人建立的长期页面（前台不说“个人主页”） | 进入 TA的主页 |
| PRD/内部分层 | `个人主页` | 否 | 围绕身份建立页面的内部能力名 | 内部分层 |
| 设置/管理语言 | `子账号` | 可局部使用 | 多身份管理场景下的产品词 | 子账号管理 |
| PRD/技术术语 | `SubAccount / 子账号` | 否 | App 世界的默认主体 | 发内容、加群、聊天 |
| PRD/技术术语 | `OwnerAccount / 主控账号` | 否 | 登录、安全、恢复、设备与通讯录发现容器 | 登录态与恢复 |
| 搜索/聊天用户词 | `联系人` | 是 | 可用于搜索、聊天、通讯录发现的人 | 搜索联系人 |
| 关系概念 | `关注` | 是 | App 内唯一社交关系概念，由 `FollowEdge` 表达 | 关注 TA、已关注 |
| 关系派生状态 | `互相关注` | 可前台使用 | 双方各有一条关注边的状态描述，不是新的关系等级 | 你们已互相关注 |
| 用户主页统计词 | `粉丝` | 是 | 关注了我的人；仅用于人页统计与列表文案，不是新的关系概念 | 粉丝列表 |
| 门禁动作 | `拉黑` | 是 | 用户到用户的对象级阻断动作，由 `BlockEdge` 表达 | 拉黑 TA |
| 消息流程 | `打招呼` | 是 | 非互相关注用户进入私信前的请求箱流程 | 向 TA 打招呼 |

### 使用规则

- 前台默认先说 `身份`，不是 `主控账号`
- 前台说 `我的主页 / TA的主页 / 作者主页`，不把 `个人主页` 作为前台词
- `OwnerAccount` 不能被当成 App 世界的默认主体
- `联系人` 不等于 `用户主页`，在搜索与聊天语境中优先表示“可发起或进入会话的人”
- 全 App 只有一个关系概念：`关注`；不得把好友、同好、密友、挚友作为关系等级使用
- `互相关注` 只是关注状态描述，不得包装成新的关系概念
- 前台统计词统一：人页用 `粉丝`，地点和事物页用 `关注`，圈子/讨论型社区用 `成员`；前台不使用 `关注者`
- `拉黑` 是门禁动作，不是关系等级；`打招呼 / 私信 / 会话` 是消息流程，不是关系等级

## 5. 主页体系

| 层级 | 术语 | 是否前台使用 | 定义 | 示例 |
|------|------|-------------|------|------|
| 泛称 | `主页` | 可在上下文清晰时使用 | 长期承接某个主体或事物的信息页面 | 进入主页 |
| 用户语言 | `我的主页 / TA的主页 / 作者主页` | 是 | 围绕某个人建立的主页（不说“个人主页”） | 查看作者主页 |
| 用户语言 | `车型主页 / 酒店主页 / 景点主页 / 餐厅主页` | 是 | 围绕具体事物建立的主页 | 认领酒店主页 |
| PRD 术语 | `共享主页` | 否 | 对各种具体事物主页的统一能力名 | 共享主页网络 |
| 内部抽象 | `关系主页` | 否 | 群组详情页的统一抽象 | 兴趣型 / 组织型 |
| 技术术语 | `entity-service` | 否 | 共享主页域的云侧服务名 | `entity-service` |

### 使用规则

- `主页` 是泛称，不独占某一种页面
- 前台用对象名（`我的主页 / TA的主页 / 作者主页`、对象名 + 类型标签、圈子名、组织名），不暴露 `个人主页 / 共享主页 / 关系主页` 这三个工程抽象词
- 内部分层有歧义时可写 `个人主页 / 共享主页 / 关系主页`，但落到前台必须改对象名
- 前台不出现 `实体`、`directory`、`对象平台`、`社群`（作 Tab / 标题）
- PRD 内部分层可用 `共享主页`；服务层保留 `entity-service`

## 6. 群组与关系沉淀

| 层级 | 术语 | 是否前台使用 | 定义 | 示例 |
|------|------|-------------|------|------|
| 兴趣型对象 | `圈子` | 是 | 兴趣型可加入对象（兴趣型关系主页），不作全局总称；底栏承载是 IA 决策 | `摄影圈`、`L9车友圈` |
| 详情页类型 | `学校 / 院系 / 班级 / 公司 / 部门` | 是 | 组织型关系主页的前台名称 | `复旦大学`、`推荐算法部` |
| 子单元 | `群` | 是 | 关系主页内的可加入子单元 | 公共群、自建群 |
| 群类型 | `公共群` | 是 | 由关系主页管理侧创建的群 | `华东公共群` |
| 群类型 | `自建群` | 是 | 成员自组织创建的群 | `摄影小组` |
| 群类型 | `班级群` | 是 | 学校组织型关系主页下的班级节点所绑定的群会话 | `2020级3班` |

### 使用规则

- `圈子` 只表示兴趣型对象，不作全局总称；底栏一级入口名称与承载由 `circle-community` 与首页/圈子会话定夺
- `群组` 不作为前台一级入口总称
- 组织型详情页前台直接显示具体类型或节点名（学校 / 院系 / 班级 / 公司 / 部门）
- 群不是聊天的同义词，聊天只是群的一种能力
- 学校、院系、班级、公司、部门等需要成员和群治理时，归组织型关系主页；若同一对象也有共享主页，后者只承接口碑、内容挂载和相关群组摘要
- 班级群不是新的会话类型；它是班级节点绑定的群会话

## 7. 内容与发布

| 层级 | 术语 | 是否前台使用 | 定义 |
|------|------|-------------|------|
| 动作 | `发布` | 是 | 全局统一内容动作 |
| 内容类型 | `笔记` | 是 | 轻量记录、动态、经验、攻略类内容 |
| 内容类型 | `作品` | 是 | 完成度更高、展示感更强的内容 |
| 内容类型 | `提问` | 是 | 面向求助、咨询、问答场景的内容 |
| 内容类型 | `口碑` | 是 | 绑定共享主页的结构化评价内容 |
| 表达形式 | `图文 / 视频 / 文章` | 是 | 用户开始创作的方式 |
| 发现/投影视角 | `微趣 / 美图 / 视频 / 文章` | 可前台使用 | 发现流里的展示或内容家族视角 |

### 使用规则

- 全局统一叫 `发布`，不全局统一叫 `发帖`
- `发帖` 仅可在明确论坛语境中局部使用，不得作为全局动作名
- `口碑` 必须绑定一个共享主页
- `笔记 / 作品 / 提问` 可选择绑定共享主页
- `笔记 / 作品 / 提问 / 口碑` 是业务内容类型
- `微趣 / 美图 / 视频 / 文章` 是发现或媒体展示维度，不与业务类型混为一层

## 8. 会话与消息

| 层级 | 术语 | 是否前台使用 | 定义 |
|------|------|-------------|------|
| 产品词 | `消息` | 是 | 底栏第四项，聚合会话、联系人、@我、@小趣回复与提醒 |
| 用户语言 | `会话` | 是 | 一个实时沟通上下文 |
| 用户语言 | `消息` | 是 | 会话里的单条沟通内容 |
| 用户语言 | `聊天记录` | 是 | 搜索和查看记录消息时的说法 |
| 用户语言 | `会话列表 / 收件箱` | 可前台使用 | 会话聚合入口 |
| 技术术语 | `Conversation / Message` | 否 | 会话与消息域核心对象 |
| 技术术语 | `CircleGroup` | 否 | 圈子或组织型关系主页下的群单元；可绑定 `Conversation` |

### 使用规则

- `群` 不等于 `会话`
- 群可以有会话，会话也可以独立于群存在
- 搜索里优先说 `聊天记录`，不直接暴露 `Conversation`
- 圈子群、班级群、自建群、临时群在会话域统一落到 `group` 主语义，不作为前台并列会话类型
- 会话内小趣是助手成员，不是新的会话类型

## 9. 助手与搜索

| 术语 | 是否前台使用 | 定义 |
|------|-------------|------|
| `小趣` | 是 | 全局统一助手名 |
| `小趣搜` | 是 | 搜索里的 AI 结果入口 |
| `@小趣` | 是 | 在会话内提及小趣并触发助手回复 |
| `全局搜索` | 是 | 跨内容、联系人、聊天记录、圈子与后续主页的搜索壳层 |
| `搜索 + 小趣全局入口` | 是 | 所有一级页顶部共享入口，搜索进入全局搜索，小趣进入个人助手会话 |
| `最近在搜` | 是 | 搜索首页记录区块 |
| `网络结果页` | 是 | 搜索 query 进入后的综合结果页 |
| `Run / Stream / 学习事件 / 反馈注入` | 否 | 助手运行与学习闭环的内部术语 |

### 使用规则

- `小趣` 是产品词，不直接让用户理解 `assistant-run-learning`
- `小趣搜` 只用于搜索结果语境
- 搜索页的统一用户词是 `群组`，不是 `圈子`
- 会话内使用 `@小趣` 表达助手参与；内部实现为 `ConversationMember.memberType=assistant` 与 `assistant_reply` 消息

## 10. 分发与挂载

| 术语 | 是否前台使用 | 定义 |
|------|-------------|------|
| `话题` | 是 | 内容分发与聚合锚点 |
| `地点` | 是 | 与地理位置相关的分发与浏览锚点 |
| `关联主页` | 是 | 内容与某个具体事物主页的绑定 |
| `相关群组` | 是 | 主页推荐的关系沉淀入口 |
| `发现流` | 是 | 推荐内容主消费流 |
| `标签 / tagRef` | 标签名前台可见，路径内部 | 路径制 taxonomy 节点（`Topic / Audience / Format / Entity`），全 App 唯一标签真相源 |
| `交集理由` | 文案前台可见，结构内部 | `dimension + tagRefs`（关系维度用 relationRef），端只展示不拼装 |

### 使用规则

- `话题`、`地点` 不替代共享主页
- `话题 / 标签` 唯一真相源是数据工程路径制 taxonomy（`publish/tags`，`tagRef`）；禁止新造扁平标签枚举，废弃 `tag_taxonomy.yaml`
- `内容挂载主页` 优先于“创建抽象对象”的用户心智

## 11. 角色体系

| 场景 | 正式术语 |
|------|----------|
| 兴趣型关系主页 | `圈主 / 圈管` |
| 组织型关系主页 | `负责人 / 管理员` |
| 群级 | `群主 / 群管` |
| 共享主页维护侧 | `创建者 / 贡献者 / 维护者 / 认领方` |

### 使用规则

- 学校、公司、院系、班级等不得再用 `圈主`
- `群主` 只属于真实的群单元
- 共享主页认领方不等于内容与口碑拥有者

## 12. 禁用或仅内部使用术语

| 术语 | 处理方式 | 原因 |
|------|----------|------|
| `实体` | 前台禁用，内部可用 | 太技术，不符合用户语言 |
| `directory` | 不作为整域名和产品主词 | 更像黄页/目录，不适合主页网络 |
| `对象平台` | 禁用 | 用户难以理解，语义过宽 |
| `圈子` 作为全局总称 | 禁用 | 会与学校/公司等组织型主页冲突 |
| `社区` 作为全局总称 | 不建议 | 过泛，弱化组织与群的边界 |
| `发帖` 作为全局动作 | 禁用 | 论坛语义过强，覆盖不了作品/动态/口碑 |
| `官方群` | 不作为前台主词 | 后台感过强 |
| `私有群` | 可作为规则描述，不作为一级产品词 | 用户更容易理解 `自建群` |
| `个人主页 / 共享主页 / 关系主页` 作前台词 | 前台禁用，内部分层可用 | 工程抽象，用户听不懂；前台用对象名 |
| `社群` 作按钮 / Tab / 页面主标题 | 禁用 | 过泛，与圈子 / 组织 / 群心智冲突 |
| 无来源的“猜你喜欢”式理由文案 | 禁用 | 交集 / 推荐理由必须可溯源到 `dimension + tagRefs` |
| 扁平标签枚举（`tag_taxonomy.yaml` / `topic_*`） | 废弃清理 | 标签唯一真相源是路径制 `tagRef` |
| `旧关系等级名称` | 禁用 | 与“关注”为唯一关系概念冲突，会产生二义 |
| `旧关系等级字段` | 禁用 | 旧关系双轨，必须删除而非兼容 |
| `同频` / `广场` 作前台主词、底栏标签、页面标题 | 前台禁用（历史原型名，内部迁移备注可用） | 泛化、与北极星「交集」脱节；2026-06-30「交集行动重建」后前台统一为「同趣 / 找同趣 / 兴趣配对」，旧 `plaza / connection` 原型已下线 |

## 13. 当前口径

| 当前口径 | 使用场景 |
|----------|----------|
| 群组 | 圈子、群聊、兴趣群的统一上位词 |
| 圈子 | 兴趣型群组 |
| 学校 / 公司主页 | 组织型关系主页 |
| 班级群 | 组织型关系主页下班级节点绑定的群会话 |
| 共享主页 | 地点和事物的对象主页 |
| 发布 | 内容创建动作 |
| 内容流 | 内容消费流 |
| 公共群 | 对外可发现群 |
| 自建群 | 临时或私有群 |
| 负责人 | 圈主在学校/组织场景的统一称呼 |
| 我的主页 / TA的主页 / 作者主页 | 个人主页语境 |
| 地点和事物（对象名 + 类型标签） | 对象主页语境 |
| 路径制 `tagRef` | 标签唯一真相源 |
| `dimension + tagRefs` | 交集与推荐理由表达 |

## 16. 后续 PRD 检查清单

任何新 PRD、设计稿或 metadata 规划，在落笔前都要先过这几个问题：

1. 这个功能面对用户时，看到的是哪一个正式术语？
2. 这个术语属于前台用户语言、PRD 术语还是技术术语？
3. 是否误把 `圈子` 当作全局总称使用（圈子只能是兴趣型对象）？
4. 是否误把 `实体 / directory / 个人主页 / 共享主页 / 关系主页 / 社群` 等抽象或内部词暴露给用户？
5. 是否把 `群` 和 `会话` 混成一个对象？
6. 是否把业务内容类型与发现展示维度混成一个维度？
7. 是否违反了“人 / 地点和事物 / 圈子 / 组织 / 群 / 内容 / 会话”这套用户语言对象分工？
8. 涉及标签时，是否统一用路径制 `tagRef`（未新造扁平标签枚举）？
9. 涉及推荐 / 交集理由时，是否可溯源到结构化 `dimension + tagRefs`（无无来源文案）？
10. 涉及社交关系时，是否只使用 `关注` 一个关系概念，并把拉黑、打招呼、私信、联系人分别归为门禁、流程和视图？

只要有一项回答不清，就先补术语，不直接进入实现。

### 18.2 修订（覆盖旧口径）

- 消息页二级分类 `群聊` ~~改为 `讨论`~~ **回滚保留 `群聊`**（见 18.6）；`私聊` 保留（user×user 会话不是群概念）。

### 18.6 消息域群会话命名回滚（「发起群聊商用重构」会话冻结）

> 由「发起群聊商用重构」会话冻结。WP5 曾把 chat-conversation 群会话前台词统一为「讨论」，实测「讨论」对群会话场景表意弱、用户认知成本高（多人聊天直觉是「群聊」）。本小节将**消息域 / chat-conversation 群会话**前台词回滚为「群聊」，是对 18.2 中聊天群会话条目的反向修订；与 18.1 / 18.2 冲突时，凡涉及 chat 群会话，以本小节为准。

**回滚边界（仅限 chat-conversation 群会话）：**

| 场景 | WP5 口径 | 回滚后（本小节） |
|------|----------|------------------|
| 消息页二级筛选「群聊」胶囊 | 讨论 | **群聊** |
| 联系页二级 Tab（`contactsTabGroups` / `contactsTabFunGroup`） | 讨论 | **群聊** |
| 发起入口（加号 → 发起群聊 / Web 创作社交区） | 发起讨论 | **发起群聊** |
| 群管理 / 群名称 / 退出 / 解散 等会话管理文案 | 讨论… | **群聊…** |
| Web 宽屏壳消息 Tab 与消息搜索提示 | 讨论 | **群聊** |
| 登录门（发起群聊 continuation） | 发起讨论 | **发起群聊** |

**保持「讨论」不回滚（内容讨论分区，非 chat 群会话）：**

- 实体主页「讨论」Tab（`objectTabDiscussion` / `homepageDiscussion*`）。
- 圈子内容「讨论」Tab 与频道管理（`circleGroups` / `circleManageChannels` 等）。
- 全局检索跨对象聚合「讨论」分区（`_shared/search_objects.yaml` 的 `circle.group` / `group` / `groups`，聚合 circle + circle.group，非 chat-only）。
- 交集六类母表达「共同讨论」（`coCommented`）。

**约束：** wire/type/filter 标识仍为 `group`（契约不变，仅前台展示词回滚）；门禁 `verify_concept_naming.py` 已将「群聊」移出禁用词、保留「群组 / 趣群 / 讨论群 / 空间 / 频道 / 论坛」为禁用。
