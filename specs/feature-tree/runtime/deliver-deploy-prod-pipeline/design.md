# L2 Design：生产交付管线 (`deliver-deploy-prod-pipeline`)

> 对应规格：[L2 spec](./spec.md)

> 设计触发原因：“以 `alpha-local`、`beta-local`、`gamma` 本地镜像和 `prod-hosted` 为环境边界，由 `stackctl` 与 GitHub Actions 统一完成打包、启动、健康检查、端云验证、灰度发布与回滚”需要 `daily-merge-release-strategy`、`gray-release-to-prod`、`local-gamma-mirror`、`multi-environment-instance-isolation`、`multi-environment-wave-deployment`、`workflow-naming-consolidation` 共享状态 owner、契约或质量边界。

## 1. 背景、目标与非目标

- 设计目标：让本地环境生产源码质量、GitHub验证不可变信任，并以RC资格与stable标签选择解耦main最新源码和Prod激活。
- 非目标：复制字段 schema、实现任务、测试排列组合或执行历史。
- 生产治理边界：`administrative` 只合并冗余人工审批与同一 exact 输入上的重复 CI，复用仍验证证据有效期与前驱身份；main/stable、签名物料、health、Provider、回滚/恢复技术门和失败终态不放宽，不授予直接放量权。正式生产仍消费各 owner 的现有技术事实与操作授权，未实测 OPEN 保持不变。

## 2. Story 协作与状态流

- [`daily-merge-release-strategy`](./daily-merge-release-strategy/spec.md)：scoped candidate 在 lane 完成 required source checks 与 typed Alpha/Beta（live 显式 opt-in）并形成 bundle，同一工作树验真 admission 后由受信发布通道 non-force fast-forward 更新 dev；`dev1.0 -> main` 只做可用源码 promotion。
- [`gray-release-to-prod`](./gray-release-to-prod/spec.md)：**统一入口**：workflow 与人工命令最终都收敛到 `stackctl deploy --target prod-hosted ...`。
- [`local-gamma-mirror`](./local-gamma-mirror/spec.md)：integration scheduler只对current exact dev head生产Gamma与晋级资格。
- [`multi-environment-instance-isolation`](./multi-environment-instance-isolation/spec.md)：不同 target 可并行，跨 worktree 同 host-target 只有一个运行 generation；同身份启动 attach 复用，不同身份显式冲突，更新需独占 mutation 与 lease 协调。
- [`multi-environment-wave-deployment`](./multi-environment-wave-deployment/spec.md)：按 alpha、可选 beta、gamma、prod 的前驱准入发布同一制品，选中波次失败即停止晋级；Beta 未选只消费合法政策跳过，不伪造 passed。
- [`service-core-composition`](./service-core-composition/spec.md)：以同一 Go host 组合 11 个核心服务而不改变领域契约、数据归属或独立实时/模型故障域。
- [`workflow-naming-consolidation`](./workflow-naming-consolidation/spec.md)：**约束**：不得保留重复名称（如 05/05b、08b/08b）或依赖旧的 `workflow_run` 定时合流链。

## 3. 端云与数据流

- 上游能力：[`runtime`](../spec.md) 声明的领域入口。
- 下游能力：本目录直接 Story 及其公开结果。
- canonical 引用：`quwoquan_ops/environments`、`quwoquan_ops/environments/prod/kustomization.yaml`
- 一致性要求：遵循本层或父 L1 DEC 声明的一致性边界。

## 4. 关键决策

<a id="dec-001"></a>
### DEC-001 源码晋级、发布资格与生产激活采用分离的不可变身份链
- 决策：以下 dev admission 约束由本地受管入口强制；服务端普通授权凭据可 FF 的缺口按 DEC-011/OPEN-004 如实 track，不阻塞有效本地合入。源码 writer 在现有 lane 以私有 Git index 和不重叠整文件 scope 构造 `ExactIntegrationCandidate`；integration/dev 的环境 consumer 身份不授予 lane acceptance producer 身份；lane 验收在 exact candidate 上完成 required source checks、Alpha 与显式 opt-in Beta，产出 acceptance bundle。唯一 `integration/` 工作区只消费并验真该 bundle，在本地 FF 前检查 current remote parent，最终 publisher 独立复验 exact admission、前驱签名/有效期、candidate/tree、before/after、路径/remote 与 ancestry 后，以 expected-old non-force FF 更新 `origin/dev1.0`。不存在普通认证 source-only 旁路，env=1 不证明 admission。`integrationEligibility` 由 exact admission 建立，push 不重新签发环境或后续资格；integration scheduler 仅对已发布 current exact dev head 生产 Gamma 与 `IntegrationQualificationFact`，`dev1.0 -> main` PR 产生 MainSourceSeal 后由受管 system backsync 更新 dev，再回同步本地 identity。缺任一证据保持 typed blocker，后续 release/Prod 仍消费原有资格链。
- 决策：`dev1.0 -> main`是availability promotion而非release pipeline。唯一required context只验证synthetic merge tree、current refs、审批、ruleset和不可变IntegrationQualificationFact；合入后`MainSourceSeal`证明source-admitted。GitHub promotion禁止执行build、源码测试、ABG、Provider live、设备与环境命令，SLI只计算`promotionReadyAt -> mainReadbackAt`。
- 决策：`main`是最新可用源码，不是待发布版本或Prod selector。普通main push零build、零tag、零production effect；临时验证只使用无Git ref的SemVer-compatible dev artifact identity。
- 决策：`ProductVersionManifest`是目标SemVer的唯一authoring source，单一active release train。发布意图由annotated `vMAJOR.MINOR.PATCH-rc.N`锚定main-reachable commit；RC按受控请求声明交付目标及真实依赖触发build/sign/SBOM/provenance once与适用证据归约；App移动包目标仍要求最终签名包/Provider/UAT/物理设备接受，服务目标不外推App资格，生成限定范围的`QualificationFact`（见`DEC-008`）。源码、版本投影或material变化必须创建下一RC。
- 决策：product owner选择qualified RC，release owner批准campaign，唯一controller在独立Environment授权后创建同commit、同material/build number/digests的annotated `vMAJOR.MINOR.PATCH`，并经Hosted readback形成`ReleaseTagAdmissionFact`。RC与stable ref均create-only，update/delete无bypass；stable不重新构建。
- 决策：Prod唯一输入为stable tag AdmissionFact绑定的exact OCI digests、source/control-plane SHA与受信prior存在性前驱（`REQ-005`：present绑定previous-stable ledger，absent绑定未激活安全态证据）。production approval后只物化一次，由`stackctl`在同一事务完成`canary -> 5 -> 20 -> 50 -> 100`；有prior的回滚只选择ledger证明的历史released digests；无prior失败只允许按`DEC-008`恢复受管未激活安全态，不制造旧版本。`main HEAD`、裸SHA、latest、repository variable和transport tag均不是authority。
- 决策：证据链采用canonical JSON、DSSE/in-toto envelope与create-once OCI/hosted append-only store；后继引用前驱exact bytes。切换后只接受当前schema；兼容读取、并行写入、可变指针降级和workflow success推导全部禁止。
- 并发与恢复：candidate parent/CAS漂移使candidate及A/B事实失效；unknown ref update先按before/after/other readback。Gamma被新head替代时未mutation任务取消，已mutation任务只安全teardown并记录superseded。promotion backsync仍使用expected-before fast-forward CAS，分叉阻断。
- 五分钟观测：目标p95固定300秒，enforcement budget只可由固定UTC 14日全样本窗口、nearest-rank p95和连续K个qualified窗口单调收紧；不使用阶段状态、success-only、rerun重置、样本过滤或放宽例外。
- 理由：把本地质量生产、托管信任验证、产品发布选择和运行激活分开，既能把源码晋级压缩到API验真级延迟，又不会把main最新状态或标签名误当作已验证制品与生产状态。
- 被否决方案：main push重跑ABG/build并自动Prod、GitHub self-hosted生产本地环境事实、RC到stable重建、标签移动/删除、latest-qualified自动选择、按版本号猜回滚、临时成熟度阶段与长期兼容双轨。
- 关联要求：`REQ-001`、`REQ-003`
- 影响 Story：[`daily-merge-release-strategy`](./daily-merge-release-strategy/spec.md)、[`gray-release-to-prod`](./gray-release-to-prod/spec.md)、[`local-gamma-mirror`](./local-gamma-mirror/spec.md)、[`multi-environment-wave-deployment`](./multi-environment-wave-deployment/spec.md)、[`workflow-naming-consolidation`](./workflow-naming-consolidation/spec.md)
- 关联验收：`SIT-001`

<a id="dec-002"></a>
### DEC-002 prod-hosted 单机与多机共享 canonical inventory 完整性边界
- 决策与 owner：`quwoquan_ops/environments/prod/access-isolation.yaml` 唯一拥有 `management.hosts` 与 `deploymentInstances.{prevalidate,gray,prod}.replicas`；`prod_hosted_topology.py` 只做完整性查询与运行投影，`stackctl` 是唯一部署 effect 入口，`deploy_to_prod.sh` / `render_prod_plane_stack.py` 消费同一 inventory，service-plane hosted ledger 独占聚合 CAS 与正式结果。单 host、每执行 plane 一个 replica 与合法多 host 配置使用同一个算法，不新增环境、版本或模式，不保留至少两 host 的旧门或单机兼容入口。
- 期望集合与 mutation 边界：从当前 stage 对应 instance 的完整 canonical inventory 派生全部 service/edge placement，再比较执行计划是否完整一致；不得把 host/plane/service 过滤后的计划反向定义为 expected。所有 host 必须属于 inventory、支持对应 plane 且管理端点一致；replica identity 在 instance/plane 内唯一，同 instance/plane 同 host 不得重复绑定固定发布口，service/edge 及 gray/prod 的 identity/host 共置必须匹配。空集合、缺项、重复、端口冲突或错误 host 在首个远端 mutation 前返回现役 typed `GATE_BLOCK`，不只删除数量判断后放行。
- 一致性与幂等：每个 placement 保持独立 remote root / project / unit / `SERVICE_INSTANCE_ID` 与 config ACK；从真实执行追加的 receipt/readback 按本次 instance、host、plane、replica、candidate/config digest 对照完整 expected 集合。覆盖必须逐一且唯一，重复证据不可通过字典后写覆盖消失，错 host、意外 placement、缺项、失败或摘要漂移均不得满足 CAS。聚合前复核同一 inventory 与 existing ledger generation；inventory 或 expected generation 漂移即阻断，不重算更小集合追认部分成功。同一 canonical command 的幂等重放沿既有 ledger 身份读回，失败 retry 仍追加新 attempt，不引入第二 ledger/event authority。
- 失败与恢复：拓扑门通过不授予 release authority；权限、安全、容量、Provider、数据恢复、正式资格、审批和 health/SLO 门全部保留。mutation 前失败不执行远端动作；已有部分远端执行时停止后续放量，保留各 replica 原始结果，不写 `full`，outcome 未知先 hosted readback，再依 `DEC-008` 的 prior 存在性及对应恢复证据恢复（present 使用 exact previous released，absent 回到未激活安全态），禁止猜测 baseline、改写 receipt 或清理未拥有的工作负载。整机不可达时不能承诺在同 host 自动恢复，保留 typed blocker 与 `OPEN-002`，不以配置正确声称恢复成功。
- 观测与 SLO：报告绑定 inventory、instance、expected/observed placement、candidate/config digest、ACK、CAS generation 与首个 typed blocker；required placement 的 receipt/ACK 覆盖目标为 100%，缺失、重复、失败、错 host 与漂移计为阻断并进入既有发布告警面。容量、延迟、错误率、回滚预算和 soak 窗口只消费既有 canonical policy，不在本决策另设阈值。单机明确记录 candidate/stable 峰值资源竞争及宿主故障同时影响 service/edge 的范围；未取得实际容量/恢复证据不宣称跨故障域 HA、零中断或新的 RPO/RTO。
- 测试 seam：`local_contract` 绑定 `SIT-002`，以完整单 host 与多 host inventory 为同算法正例，覆盖过滤子集、缺 plane/placement、重复 replica、发布口冲突、未知/错误 host、管理端点及共置漂移；receipt 缺项/重复/失败/错 host/摘要漂移、CAS 前 inventory 或 generation 变化均证明零成功聚合。入口合同同时覆盖 `stackctl prod-hosted-plan`、正式 deploy 与底层部署调用，禁止旧数量门/兼容开关残留；`api_integration` 以授权目标的逐 replica receipt/ACK、health/SLO 和 hosted CAS readback 验证真实边界，未执行部分留在 `OPEN-002`。
- 理由：发布拓扑的必要条件是已声明执行面完整且可验证，不是固定的主机数量；容灾能力则必须由真实故障域与恢复证据独立证明。这样单机与扩容共享同一发布安全边界，不把 inventory 完整性误当高可用或发布资格。
- 被否决方案：硬编码至少两 host/每 plane 两 replica、单机豁免开关、V1/V2 或历史兼容分支、`prod-gray` 环境、另建 topology 真相源、host override 改写正式 inventory、过滤后按子集验收、重复 receipt 后写覆盖、按 replica 独立 ledger 绕过 service-plane CAS。
- 关联要求：`REQ-002`
- 影响 Story：[`gray-release-to-prod`](./gray-release-to-prod/spec.md)、[`multi-environment-instance-isolation`](./multi-environment-instance-isolation/spec.md)；本决策不修改 App/Service 资格、首次 previous baseline 或灰度/soak 门槛。
- 关联验收：`SIT-002`；未实现的 inventory 门与单机容量、恢复、正式 readback 由本层 `OPEN-002` 保留。

<a id="dec-003"></a>
### DEC-003 核心 Go 服务以 Service Core 组合部署且保持 split-ready
- 决策：`api-edge`、`assistant-service`、`chat-service`、`circle-service`、`content-service`、`entity-service`、`integration-service`、`notification-service`、`search-service`、`tag-service` 与 `user-service` 组合为一个 `service-core` Go 进程、镜像与部署单元，Python `recommendation-service`、`realtime-gateway`、`rtc-service`、`product-ops-service` 与 `platform-ops-service` 保持独立进程，组合不改变服务 contracts、公开 hostname/port/route、数据源、迁移 owner 或可观测 `service.name`。
- 理由：核心服务共享受治理运行时和同一发布节奏，组合可减少单机部署开销，Python 模型运行时及长连接服务具有不同语言、资源和故障恢复特征，继续独立可避免将其扩散为单 PID 故障域。
- 被否决方案：把所有服务、实时、RTC、模型和运维服务合并为一个进程，或为组合部署合并领域，或让 module 间以私有 import/共享 store 直接调用，或在一个 target 并存两套 topology 或运行时切换。
- 约束与影响：模块只暴露自身薄 bootstrap，顶层 host 只组合 module factory，module 间仍经原 generated HTTP/WS contract，workload composition 从服务自治部署输入生成，候选同时绑定 OCI、SBOM、provenance、module/config/migration digest，切换为整体 candidate 操作，回滚只使用上一 immutable candidate 的精确 bytes，host 按 module 执行配置、迁移、listener admission、health、资源预算、shutdown 和 observability，任一 required module 的不可恢复失败使 aggregate fail-closed。
- 关联要求：`REQ-002`
- 影响 Story：[`service-core-composition`](./service-core-composition/spec.md)
- 关联验收：[`service-core-composition GWT-001/GWT-002`](./service-core-composition/spec.md#gwt-001)

<a id="dec-004"></a>
### DEC-004 App 制品身份、签名隔离与多渠道分发回执
- 决策：App 分发以三个分离对象承载事实——`AppArtifactManifest`（属于 `app_factory_material` / `CandidateMaterialManifest` exact-byte 物料闭包、由 app factory producer 写入实际 payload 并由 qualification reducer 验证的 immutable owned entity，不属于 `ReleaseEvidenceManifest`；拥有 platform、BuildMode、distributionClass、package/bundle ID、version/build、signing identity、source/artifact/launch-manifest digest 与 promotability）、`InstallReceipt`（按 store/device/build 追加且集合无界的 separate append-only fact，独立生命周期与查询）、渠道矩阵（从 canonical metadata 生成，覆盖 Apple App Store/TestFlight、华为、小米、OPPO、vivo、应用宝与官网 `official_web` APK）。打包、签名校验、安装与渠道登记统一走 `stackctl package` 的 canonical App 入口（显式 `env/platform/build-mode/distribution-class/device`），`run.sh` 与 IDE 只做薄包装。
- 跨边界 port：构建写入走 `AppArtifactPackageWriter` 生成不可变制品、`AppArtifactManifestReader` 提供验证查询；安装证据走 `AppInstallReceiptAppender` 只追加真实安装/商店回执、`AppInstallReceiptQuery` 供准出读取。禁止脚本或 Provider 直连绕过 port。
- 包身份隔离：Release 只按 canonical nonprod/prod 信任域使用两套 application/bundle ID 与签名映射——Android/iOS Prod Release 为 `com.leadwise.quwoquan`，nonprod Release 为 `com.leadwise.quwoquan.nonprod`。仅不可提升的 Alpha/Beta/Gamma Debug/Profile 可按 `com.leadwise.quwoquan.<env>.<mode>` 生成独立安装身份以支持并存调试；这些制品必须 `nonPromotable=true`，不得进入 RC、市场或官网，Prod Debug/Profile 不生成且无入口。同设备切环境结束旧绑定后重建运行上下文；Release 不以环境包名、覆盖安装或重编实现切换。
- 正式身份来源：仓内冻结字符串只是候选配置，不自行证明外部登记。Prod 正式 ID 只有在对应平台与渠道权威 readback 一致后才成为已登记外部事实；Android 当前可消费 vivo 已登记 readback，iOS Apple Developer/App Store Connect readback 未完成前继续阻断。所有 nonprod 与 Debug/Profile 隔离身份必须同步 Universal/App Links、OAuth、推送与 Keychain/App Group。
- 签名分发边界：Debug 签名制品仅限开发者本机、Simulator/Emulator 与登记设备；TestFlight、市场与官网只接受 Release。
- 制品格式与渠道解耦：`AppArtifactManifest` 携带显式 `artifactFormat(apk/aab/ipa/app/web)`，由打包请求声明或按平台默认推导，禁止由 distributionClass 推导（原 `store → AAB` 耦合废除）；官网与全部 APK 市场引用同一 release APK source digest，`aab` 仅当已启用渠道 capability 硬性要求时按 DEC-005 构建一次。
- 正式 Android/iOS Release 候选身份均冻结为 `com.leadwise.quwoquan`；Android 的 vivo 开放平台已有登记外部事实，Java namespace 与 applicationId 分离，微信回调 Activity 按 applicationId 约定放置。iOS 字符串已由产品确认但仍缺 Apple 权威登记 readback，所有依赖该登记的 store 渠道保持阻断。
- 渠道逐项声明：每渠道登记 `channelId`、`uploadFormat(ipa/aab/apk)`、package/bundle ID、store product ID、track、version/build、developer signing identity、store signing custodian、可能的 split/optimize/re-sign transformation、source candidate/artifact/launch-manifest digest、upload/review/release receipt 与安装后 signature/receipt 校验方式。`uploadFormat` 只声明渠道接受能力，不驱动构建。市场可能重签或优化，准出不要求下载二进制逐字节相同，而以 source digest、version/build、store 官方签名/receipt、嵌入 launch manifest 与启动 telemetry 绑定；一个渠道的回执不得替代另一渠道。
- 官网分发：Android 官网 APK 复用 official distribution 部署到不可变 CDN 对象并出带 SHA-256 的 receipt，发布前通过包名/签名证书摘要/Build/SHA-256 预验证门禁；`app_release` 契约字段是恢复页、更新提示与网页安装组件共用的唯一下载真相源。iOS 网页版不提供二进制下载。
- 灰度顺序：先内测或分阶段，再公开发布。
- 快速止损：内容 active pointer、Web current pointer 与远端配置的止损在 300 秒内完成，且不要求重新打包或再次审核。
- 商店回滚边界：已安装商店 App 不可强制回滚，服务保留商店客户端 N/N-1 兼容面，禁止把“重新发版”当唯一恢复动作。
- 被否决方案：nonprod/prod 共用安装身份、按 Alpha/Beta/Gamma 另建包名、Debug 包进入市场、要求市场下载物逐字节等同上传物、把在线 active release 绑进商店二进制、side-load 冒充市场回执。Alpha nonprod 离线快照的制品绑定不属于在线 active release。
- 关联要求：`REQ-001`

### DEC-005 组件构建身份：build once、环境无关、按 digest 复用

### DEC-008 factory actual bytes 到 Prod 终态采用单一 authority 链
- 对象与 owner：Service/App factory material producer 分别拥有其 immutable actual payload bytes；release qualification 的唯一 validator/reducer 从受控请求声明目标及真实依赖派生 required factory 集合，物化适用的 factory exact refs，验证 canonical bytes 后拥有唯一 `CandidateMaterialManifest`；release tag controller 只选择并 exact 引用同一 CMM，不生成、改写或归约物料；qualified Prod owner 独占 `ProdActivationAdmissionFact`、`ProdStageAttemptFact`、`ProdReleasedFact`、`ProdRollbackFact` 与 `PostReleaseSoakFact`；official distribution 保留 package/channel 校验与逐渠道回执，但只消费 stable admission、Qualification、CMM 与 app factory exact-byte 闭包，不拥有 release selection、admission 或 Prod authority。
- Command/query 分流：服务 formal effect command 只接受声明服务交付目标且其资格通过的 stable `ReleaseTagAdmissionFact` exact ref，并先物化 `ProdActivationAdmissionFact` envelope 后交给 `stackctl`；App distribution 则校验自身声明目标、包与渠道证据，不能消费服务资格代替；qualification 与 Prod query 只从 exact refs 回读并物化 CMM/factory actual bytes，不接受调用方字段副本。公开 `package --kind release-manifest` writer 与 formal `--release-manifest` surface 必须删除。历史诊断只暴露命名读侧 `validate_legacy_non_promotable_snapshot` / `validate_historical_release_snapshot`，不得存在 generic `validate` alias、writer、verdict、admission 或向 formal command 转接的动态 attribute/import surface。
- 一致性、幂等与物料闭包：CMM 创建前必须复验 factory actual payload 的 canonical bytes、`materialDigest`、source/tree、qualification request、RC、signature 与 attestation；Service factory 还须包含 Prod runtime config/deployment bundle exact digest，App official distribution 固定沿 stable → Qualification → CMM → app factory → `AppArtifactManifest` 取包，并继续验证 package bytes、source/tree、package/channel identity 与独立 channel receipt。workflow scalar、OCI transport tag 与 local cache 只能定位或加速，不能成为 authority。
- 最小适用范围表达：由既有 request authority 在构建前批准非空交付目标集合及其平台/渠道范围，纳入 `QualificationRequest` canonical digest；reducer 验证该集合与实际 effect/物料依赖一致，再使 CMM、Qualification、stable admission exact 引用同一声明。目标仅表达服务部署、App 分发及二者联合的适用性，不引入不同 reducer、产品版本线或发布入口；具体 wire 字段/枚举/错误仍由现役 contract owner 冻结，文档不自行造 schema。每个被声明目标都有明确 required 物料与证据集合，遗漏声明不推断为完整产品，未选目标不签发资格也不记录 passed。
- 目标与物料正交：CMM 绑定本次实际生产、经验真的物料及其用途，Qualification 仅授予请求声明目标。服务目标要求真实服务工厂/签名/测试/环境/Provider/UAT/恢复闭包；App 目标保留签名包、双物理移动平台、供应链与独立渠道证据，Simulator 始终 nonPromotable。服务部署确需 Web 静态字节时，应经现有 factory 输出携带该依赖并验真，但不因此要求非依赖移动包或授予移动分发资格；App-only 也不能因服务物料在仓内存在就取得服务部署 authority。来源 factory 名称不是交付目标，消费者不能通过字段缺失跳过依赖。
- 联合归约与幂等：继续保留一个请求、一个 CMM 与一个 Qualification 的既有 create-once 边界，只有声明集合内全部 required 结果通过才签发该范围的 qualified；联合请求的任一 App 缺项阻断联合签发，不允许从部分成功自动缩为服务目标。已声明范围沿 request→CMM→Qualification→stable 的 exact identity 不可增减，Prod/App consumer 只执行范围内目标；范围变化必须走既有新请求/RC 生命周期，不覆写旧事实、不移动 stable。缺 App 证据与未选 App 在只读 readiness 中分别呈现缺项和不适用，均不等于 App qualified；无需为非选目标生成假空包或假通过事实。
- 适用范围原子落地边界：先在 `quwoquan_ops/ci/release_qualification.py` 的 request/CMM/Qualification canonical validator 与物料归约契约中表达目标、依赖和 required evidence，并同步 `quwoquan_ops/environments/evidence/release_tag_admission_fact.schema.json`、`prod_activation_admission_fact.schema.json` 及 `quwoquan_ops/ci/release_tag_admission.py`、`qualified_prod.py` 的 exact 继承校验；再同步 `release_control.py` 参数适用性、`.github/workflows/release-qualification.yml` 的工厂调度/外部证据输入、`service_pipeline.yml` / `app_pipeline.yml` 的目标物料输出、`release-tag-selection.yml` / `deploy-prod-auto.yml` 消费和 `quwoquan_ops/cli/lib/official_distribution_release.py` 的范围拒绝。Prod materialization/ledger 中无条件 app factory digest 的验证与投影必须同一次切换为真实依赖闭包，不用空 digest 代填；Human approval、SoD、签名与 source/tree/request/RC 校验不动。切换前先验证 authoring contracts，再按实际所涉生成器执行 verify/codegen；切换后拒绝缺少声明范围的旧形状，不维护 V1/V2 或双读。尚未完成处留 `OPEN-011`，不执行发布。
- 范围失败与测试 seam：沿现役 typed 错误在首个 mutation 前阻断未授权目标、scope 缺失/漂移、物料或证据删项、Simulator 冒充物理设备及 signature/attestation/SoD 失败；修复证据后按同请求允许的 create-once 操作重试，已封存事实与 tag 不变，目标改变按新请求/RC 处理。`test_release_qualification__local_contract_test.py`、`test_qualified_prod__local_contract_test.py`、`test_release_tag_admission__local_contract_test.py`、`test_official_distribution_release__supply_chain__local_contract_test.py` 与 workflow convergence 合同直接绑定 `SIT-004`，覆盖服务/App/联合矩阵、依赖 Web 但无移动包、App-only 拒绝服务 effect、联合失败禁止降格、actual bytes 篡改和审批/签名负例；API seam 验证 actual factory refs 与 hosted admission 范围一致，App UAT/渠道仍只认真实设备与独立回执。观测按声明目标记录 required/observed evidence、exact predecessor、decision 与首错，required 覆盖目标100%；不新增时长/SLO门槛，不把服务通过率合并为App通过率。

- prior 的唯一互斥表达：Prod admission 中 prior 是必填带判别的当前存在性对象，而非 nullable previous、可选首发 flag 或两个版本 reader。present 必须有 exact previous released、其 hosted receipt/generation、可用且兼容的实际旧 digests 与 rollback readiness；absent 必须有 target/inventory/ledger-history/入口停流的 exact 只读证明、对应 Human 首发 request 及未激活安全态 recovery readiness，禁止携带伪 previous 或 candidate 自指。unknown 只作为拒绝/诊断结果，不是可晋级 union 成员。具体字段/path/错误码由 canonical schema owner 冻结，单次原子切换删除旧无条件 previous reader，保留现有真实历史 facts 字节但不兼容解释为新首发凭据。

- 首发安全态恢复事务：关闭本次 candidate 业务入口并取得完整路由/公开探针读回后，再停用 attempt-owned systemd unit/自动重启及未激活配置；未完成的操作逐项追加结果，恢复成功须同时证明没有候选业务流量、目标没有被标记为 released、owned进程不再服务、持久资源与其他工作负载未变。路由承载在本次候选或共享edge上时必须事前证明停流的独立可执行性，不能先停掉唯一控制入口后声称关闭成功。仅恢复到未激活安全态不要求业务 full health 假绿，也不降低 released 分支原 health/SLO 门；失败或unknown保留首错并告警，禁止生成 `ProdReleasedFact` 或 soak。恢复终态沿同一 rollback/recovery owner 的 current判别形态区分“恢复旧released”与“恢复未激活”，不得用旧版本rollback标签冒充；其exact admission/failed attempt/恢复前驱和hosted readback仍必需。

### DEC-010 证据签名信任根：Ed25519 私钥仅本地持有，公钥登记进仓内版本化 keyring，hosted 只验签

- 对象与 owner：`EnvironmentAcceptanceFact` 与 `IntegrationQualificationFact` 的 DSSE 签名统一使用 Ed25519；`quwoquan_ops/policies/evidence_signing_keyring.yaml` 是两个 signer identity（`quwoquan-environment-ops-local` 签 A/B/G EAF、`quwoquan-integration-scheduler-local` 签 IQF）与其公钥的唯一 authoring source，也是 signer identity 的 canonical 真相源。私钥只落在仓外 `QWQ_EVIDENCE_SIGNING_KEY_ROOT`（默认 `~/.cache/quwoquan/keys/evidence-signing`，0600），由 `make evidence-signing-bootstrap` 生成并把公钥登记为 `active`；bootstrap 幂等，keyring 改动随普通提交进入 `dev1.0`。
- Command/query 分流：签名侧（`environment_execution.py issue/qualify`、`integration_run.py`、`integration_candidate.py qualify`）签前必须证明本地私钥派生的公钥就是 keyring 中该 identity 的 active 公钥，签名编码固定 `ed25519:<base64 raw 64B>`；验签侧（`integration_qualification.py`、`generate_release_bound_environment_identity.py`、hosted `03. Delivery Gate`）只加载 PR head exact bytes 里的 keyring，按 expected signer identity 取 active 公钥验签，不读任何 secret、环境变量或 hosted variable。qualification 与 environment 两个 identity 的 active 公钥不得相同（`KEY_PURPOSE_CONFLICT`）。
- 轮换与失效：同一 identity 至多一个 `active`，历史 key 只能置 `retired`（保留 `retiredAt` 审计）且不可重新激活；验签只接受 `active`，因此轮换后未消费的 EAF/IQF（TTL 72h）自然失效，需在新 key 下重新签发。私钥泄露即 rotate 并提交 keyring，无需触碰 hosted 配置。
- 测试 seam：local contract 覆盖 keyring 结构漂移（双 active、keyId 不由公钥派生、purpose/identity 漂移、未知状态、多余字段）、错误 key 与 retired key 验签失败、私钥权限/仓外约束、bootstrap 幂等与 rotate、CLI 缺 identity 的 typed 阻断；`verify_ci_cd_evidence_contracts` 以仓内 keyring 可解析且两 identity 各有一把互异 active 公钥为门禁。
- 理由：HMAC 对称 key 要求同一 secret 同时存在于本地与 hosted，验签方随之获得签名能力，与"Gate 只验签不签"不自洽，且从未有 canonical 真相源导致 A/B/G 事实从未真实签发；非对称把信任材料变成可评审、可版本化的仓内公钥，hosted 零 secret，本地 key 可自动生成。
- 被否决方案：继续 HMAC 并把 secret 同步到 repository secrets、在 EAF `signer` 中新增 `keyId` 字段（改 schema 而收益有限，由 identity→active 公钥映射替代）、复用 App runtime config 的 Ed25519 keyring 文件（用途与轮换节奏不同）。

### DEC-012 数据面绑定只在部署面解析，并支持物理共址与可逆拆分
- 决策与对象边界：每个 target 的 runtime 装配附近以 `resources` 声明非秘密的 `physicalIdentity`、`engine` 与 `failureDomain`，以 `bindings` 将每个显式 `service.typedSlot` 映射到 `resource`、独立 `namespace`/`role`、`secretRef`、`backup` 与 `metrics`。`resources`/`bindings` 只属于 deployment control plane，不成为领域、服务或 App 的运行时发现 API；同一 physical resource 可以被多个显式 binding 共用，但不得据此推导默认 binding、共享 namespace 或共享 ACL。
- 唯一解析与候选身份：环境 `package` 阶段（不含 component build）是唯一 projection boundary，确定性地把 binding 解析为既有服务前缀的 URI/DSN/endpoint 与 Redis mode，再通过现有配置注入面交付应用。应用 config 与源码不得出现 `clusterRef` 候选、physical resource 选择分支或 registry lookup。candidate 只记录对非秘密声明求得的 redacted `bindingDigest`；其中 `secretRef` 只保留非秘密引用身份，secret material 与物化后的 URI/DSN/endpoint 均不进入 candidate、digest payload、日志或回执。
- 一致性、命令与幂等：binding 变更是部署控制面的显式 compare-and-swap command，输入绑定 `fromBindingDigest -> toBindingDigest`；package projection 与应用启动只查询该次已封存结果，不进行运行时重选。相同输入重放必须幂等，digest、resource identity、namespace/role、backup 或 metrics coverage 任一漂移都在应用 admission 前 `GATE_BLOCK`，不得产生部分 ready、双 reader/writer 或隐式 fallback。
- 共址与拆分：共址只表示多个 binding 显式引用同一 physical resource，各 binding 仍独立拥有 namespace、最小权限 role、备份/恢复边界、容量预算、noisy-neighbor 归因和指标覆盖。拆分不得修改应用源码、服务契约或既有配置键，只改目标 binding，并严格执行“备份验证 -> 复制 -> 追平 -> quiesce -> 原子 cutover -> readiness -> readback”；任一步失败都停止在可判定状态，并在声明的限时回滚窗口内以原 `bindingDigest` 恢复。Search 的 reader/writer 必须由同一个原子共享 binding 一起切换，禁止在追平或回滚期间分别指向新旧资源。
- 恢复、容量与观测：恢复点、复制 lag、quiesce/cutover/rollback 时长、连接/容量水位、noisy-neighbor、ACL readback、备份可恢复性与指标 coverage 均按 `binding + namespace` 记录和判定；physical resource 聚合视图只用于容量诊断，不能替代任一 binding 的证据。每次迁移 attempt 的 backup、ACL、readiness、readback 与 required metrics coverage 必须为 100%，超出 binding 的容量/SLO 或限时回滚预算立即告警并阻断晋级。
- 验证边界与测试 seam：首个非生产验证范围只在 `gamma-local`，用 production projection 路径证明“多个显式 binding 共址同一本地 physical resource”和“单个 binding 临时拆分后按上述序列切换并回滚”；local contract 证明 typed-slot 完整性、确定性 projection、redaction、共享 namespace/role 禁令、Search 原子 binding 与 CAS 幂等，Gamma 验收证明 readiness/readback 和按 binding/namespace 的恢复、容量、ACL、noisy-neighbor、metrics 证据。不得因此创建、采购或声称已验证任何 Prod 数据集群，Prod 仍保持现有外部阻断与准入要求。
- 理由：把逻辑数据所有权与当前物理部署密度分离，既允许首发以显式隔离的 namespace/role 安全共址，也能在容量、故障域或 noisy-neighbor 需要时只迁移一个 binding，且应用和候选无需感知基础设施拓扑。
- 被否决方案：在应用 config/源码保留多组 `clusterRef` 并运行时查 registry、按服务复制 physical resource 清单、因共址而共享 namespace/role、将 secret/DSN 写入 candidate、Search reader/writer 分步切换、以 dual-read/dual-write 长期过渡，或用本地演练冒充 Prod 集群建设完成。
- 关联要求：`REQ-002`
- 影响 Story：[`local-gamma-mirror`](./local-gamma-mirror/spec.md)、[`service-core-composition`](./service-core-composition/spec.md)、[`multi-environment-wave-deployment`](./multi-environment-wave-deployment/spec.md)
- 关联验收：`SIT-002`

### DEC-013 exact dev candidate rehearsal 是 prevalidate 的第二类不可提升输入，与 legacy snapshot 互斥且零正式写入
- 对象与 owner：rehearsal 候选就是 `stackctl package --env prod --target prod-hosted` 在 integration 工作树生成的 runtime-full candidate（owner：deployment control plane），其 manifest 额外声明 `materialSource=local-build`、`nonPromotable=true`、`legalStaticPlaceholder`；镜像 owner 集合与 prod 运行时镜像 owner 完全一致，每个镜像只以本机 buildx `linux/amd64` 构建一次并以 content digest 绑定进候选。legacy frozen diagnostic snapshot 与 rehearsal 候选是 `deploy --mode prevalidate` 的两个互斥输入，不存在从 rehearsal 到 formal、或从 rehearsal 到 snapshot 的转换面。
- Command/query 分流：写侧只有 `deploy --mode prevalidate --exact-candidate <digest>`，它在任何远端传输前按顺序校验：工作树干净、HEAD 等于候选 `sourceRevision`、候选等于本地 `refs/heads/dev1.0` head、候选目录位于 prod-hosted candidates 根、每个镜像本地存在且架构为 `amd64`、content digest 与候选一致；随后复用 render → local image delivery（`docker save | podman load` 并按远端 digest 读回）→ sync → user systemd → inspect 的既有 prevalidation 执行器。读侧只有 `inspect/doctor --deployment-instance prevalidate` 与 rehearsal 报告；formal rollout、`--frozen-diagnostic-snapshot`、tag/admission/ledger 路径对 `materialSource=local-build` 候选一律拒绝。
- 一致性与幂等：同一候选重复 rehearsal 只重放同一 digest；候选 digest 排除 legal 占位标记与宿主 edge 事实，因此占位状态变化不伪造新候选。隔离数据栈对 canonical immutable release 的 hosted-import/activation 只写 rehearsal 诊断，不写任何 release evidence、EAF 或 admission。

- 运行基座恢复：管理员显式授权的 bootstrap 通过同一 stackctl 入口交付固定、可追溯源码的同版 Podman，补齐 systemd 构建能力而不降级存储格式、不切换 root Docker；安装与原生 timer/健康日志增长是两层证据。构建限制 CPU、内存与最长执行时间，候选二进制验真前不替换运行时；没有真实健康读回不得将安装成功升级为部署成功。
- 秘密输入与证书保管：长期输入仓独立于源码、可删除输出和 `QWQ_DEPLOY_WORK_ROOT`，按四环境及 prod 的 prevalidate/formal 用途分开，User cohort、Provider、mTLS、App/GraphQL/Skill signer 不互借 authority。空目录仅由受管 bootstrap 准备并检查 owner/权限/非符号链接，不能据此声称 secret ready；现有 consumer 仍需显式引用、验权与挂载读回。SSH 私钥、证据签名根和宿主 Caddy ACME 存储保持原 owner，禁止为统一目录迁移或复用共存应用私钥。秘密原文不进入 provenance、receipt 或 Git；可自动续签的公网证书保留原签发器生命周期，离线 CA 与 App 签名材料另行加密备份，目录权限本身不等于加密或备份完成。
- 观测与非准出标记：报告分轴 `containerDeployment` / `providerReadiness` / `releaseEligibility`，后者恒 `GATE_BLOCK`；`legalStaticPlaceholder=true` 与 `publicEntry=host-shared-edge` 必须出现在候选 manifest 与报告中，供 verify/doctor 显式排除出 DNS/TLS、法务与发布资格判定。
- 测试 seam：local contract 覆盖 dirty tree、HEAD 漂移、非 dev1.0 head、arm64 镜像、digest 漂移、rehearsal 候选被 formal/snapshot 路径消费、legal 占位在 prevalidate 降级而在 formal 仍阻断、报告分轴与标记字段；真实单机 rehearsal 回执关闭 [`OPEN-010`](./spec.md#open-010)。
- 理由：现有 prevalidation 执行器已经具备平面隔离、rootless、digest 读回与非提升报告，缺的只是「候选来源」这一输入面；把 exact dev candidate 作为第二类不可提升输入，既能让当前候选在正式链前置（stable tag、GHCR、approval、多 member）齐备前上真实单机做端到端内部验证，又不给正式链增加任何 authority。
- 被否决方案：放宽 `_frozen_diagnostic_snapshot` 的 main 祖先校验（会让未评审源码进入正式 snapshot 语义）；在宿主用 root docker 手工 compose（第二执行面）；为 rehearsal 新建 fact schema（rehearsal 不是 authority，报告即足够）；把 rehearsal 候选直接送入 canary（违反 REQ-001）。

### DEC-017 prod-sim 复用 prod-hosted 执行面而不复制发布 authority

- `prod-sim` 只表示 `prod-hosted` 内的 non-promotable validation ring；canonical instance 映射到 `prevalidate`，沿用 hosted inventory、四平面账号、lease/fence、rootless runtime、observability 和 `stackctl` effect path。不得新增环境枚举、runner、release Fact 或本地模拟的第二准出入口。
- 生产 App 只使用 prod canonical endpoints。API Edge 的验证环 route policy 同时绑定 `displayVersion + buildNumber + artifactDigest/candidateId + target + deploymentInstance + runtimeConfigDigest`，并对可信 principal/IP 每请求 fail-closed 评估；正式 rollout assignment 的 sticky state 不得绕过验证环条件。
- 白名单语义为：账号与 device actor 白名单内部 OR；配置的用户条件与可信 IP/CIDR 条件之间 AND；版本/artifact/target 条件再 AND。两类白名单均为空时默认 disabled。Caddy 只覆盖 trusted client IP，不能复制业务策略。

- 回滚输入：执行前从目标环境已验证成功发布/activation 记录的 exact 引用冻结恢复基线，核对目标、内容摘要和可恢复字节；已知基线记录缺失、损坏、歧义或漂移时阻断，不能改为手工覆盖或扫描 `latest`。只有权威证明首次无基线时才要求操作者显式提供合法恢复输入（含既有 empty-baseline 准入），缺输入不启动。正常内容更新的 rollback 必须是 distinct 的已成功基线，不能把待验 candidate 当作伪 rollback。源码热修而内容未变时，可引用已发布内容的同一 immutable handoff/release，既有 summary 如实解释 `unchanged/no_data_change` 的含义：没有产生新内容 release，也没有完成内容版本回退；不强制造两份不同 Data release，源码/部署恢复仍绑定已成功部署基线。此语义不是新增 wire 枚举或绕过内容相等性验真。

- 最小证据与单候选 summary：原始 test/health/UAT/cleanup 报告是观测依据，沿用 source fact、EAF、admission 和 acceptance bundle 的既有 exact refs，不再为相同状态新增 fact、registry 或汇总 receipt。保留 schema/digest/signature/currentness 与 owned cleanup 校验；通过现有 summary 的 `sourceFact`/readiness、`environments`/`reports` 与 publish/readback 信息展示 source、environment、deploy 三层，不另加三份同义状态事实。环境 healthy 但 UAT 失败仍阻断环境验收与后继 admission，cleanup 失败保留首个 blocker 及清理结果，不可由上游 PASS 合成整体成功；iOS 可优先取真实 AUT 证据但不授予 App 分发资格。服务发布/App 分发的 scope 解耦由 release owner 同轨修改原合同，未实现前保持其 OPEN；范围内技术门不降级，报告归并不授予直接放量权。
- 最终组合与重验：单 lane 原样 FF 且全部 exact 输入/有效期不变时，integration 环境调用次数为零。多 lane 先在获授权的现有汇总 lane 冻结本地来源 SHA、合成最终 C 再 Alpha；不读远端 lane fallback，不用 A/B 旧 bundle 合成 C。新 commit/parent 即使同 tree、config/内容投影/用例/工具链/恢复基线漂移都须重验受影响事实；原事实不改写，CAS loser 回 lane 同步新 parent。只串行共享 ref/环境/设备，不要求其他未参与 lane 重测。
- 纯验真前置：accept 默认完整 `scope` 与 `local_readiness_scope`，源码合入只验证 source readiness 与 typed EAF；Review consolidation 与 required evidence 可选，不挡 source-admitted bundle。validate-only 与 admission 复用同一纯校验，在 HEAD/index/WIP 变化前拒绝 fast-only/缺 scope，预检不 import/admit，正式 publish 再复核。`no_live` 仍可签发 typed Alpha/Beta 并 accepted/bundle。显式与自动 candidate reuse 共用 caller owner/claim 校验，不因同 SHA 复用他方身份。
- 下游协作与 currentness：Gamma 启动、IQF、promotion 前逐次对账已发布远端 dev；漂移后旧运行只诊断，新 head 的有效 Alpha/可选 Beta 不重跑。Data sealed reader 保留，来源原件/审核成品/投影 schema 归 Data，不新增第二来源映射；release、projection 输入、API/Alpha/App 版本与媒体摘要纳入 consumer 验收。Beta 全链可选的 Data milestone 前驱合同、服务发布/App 分发解耦及单机首发由集成/Data/release owner 同轨实施：不伪造 Beta passed、previous released 或内容恢复；服务技术闭包与 App 分发门独立，模拟器 AUT 不代替分发资格；保留 main/stable、签名、Provider、法务、隔离/容量/健康/备份恢复与灰度，不要求额外第二主机、不声称 HA。
- Alpha/Beta 显式 opt-in：`derive_integration_depth` 仍派生 `abg_release_sensitive|alpha_integration|no_live`，但不决定是否真跑或政策跳过的原因码。写入 `origin/dev1.0` 是 source-admitted：默认无论集成深度为何都签 typed `not_required`（Alpha=`ACCEPTANCE.ALPHA_LIVE_DEFERRED_TO_PUBLISHED_DEV`，Beta=`ACCEPTANCE.BETA_OPTIONAL_BY_POLICY`）。live Alpha/Beta 选择延伸至 Data milestone→Gamma 全链：未选不冒充环境通过；Gamma 自身完整检查仍 required，且不得借用 Alpha 延后原因码。已选失败阻断，不自动 opt-out，新选择保留旧历史。改为 opt-in 时只在完整 runtime 前驱可恢复时复用 Alpha 补跑 Beta，否则重验。事实合同仍由 `environment_acceptance_fact_contract.NOT_REQUIRED_REASON_CODES` 唯一声明有效原因码闭集，保留 ImpactPlan 自身免环境结论的 `IMPACT_PLAN.NO_LIVE_ENVIRONMENT_REQUIRED`，但本通道不得用它代替政策原因；签发（`environment_scheduler`）、schema、admission（`create_publish_admission`）三处消费同一常量。named evidence 的 `source.basis` 与 EAF `reasonCode` 同值；ReadinessCaseResult 合同规定 passed 结果不携带 `reasonCode`，因此原因只落在 EAF 与 named evidence。
- 候选身份、基线与多 lane 合并：acceptance 的 ImpactPlan/readiness parent 默认取已发布 `origin/dev1.0` exact head；成功 publish 后下一次 delta 排除已发布变化，未发布差异增加时不承诺常量范围/耗时，真实对照仍保持 OPEN-009。可发布 parent 固定当前远端 head；candidate 已等于远端 head 时，显式历史 `--baseline` 只作诊断，否则 `INTEGRATION_RUN.NOTHING_TO_ACCEPT`。仅祖先关系不证明成功验收/发布基线；历史诊断不得重绑旧事实作为当前发布前驱。用户可显式把多个本地 lane head 合并成一个 candidate（merge commit 在当前 lane 分支上）后一次验收：`--merged-lanes lane/<name>` 只解析本地检出 identity 的 exact commit，每个都必须是 candidate 的祖先，否则 `INPUT_INVALID`；不依赖已退役远端 lane，bundle 的 `mergedLanes` 只记录来源，不改变 admission 语义。
- Command/query 分流与幂等：acceptance 默认不写 admission、不写 `dev1.0`，始终拒绝 `--acceptance-bundle`，只有显式 `--publish` 才在同一 run 内 admit 并 CAS 发布；integrate 拒绝 `--baseline`/`--alpha`/`--beta`/`--merged-lanes` 与 Data release 输入。bundle 导入幂等：同 ref 同字节跳过，`importedFiles` 记录本次新写入数。admission 的 `expectedRemoteOid` 就是 bundle 的 `expectedParent`，远端 `dev1.0` 一旦前移即 `BUNDLE_STALE`，修复路径只有在合入新 `dev1.0` 的 head 上重新 `make accept`。
- 失败与恢复：任一环境相位失败保留首个 typed blocker，只回收该 attempt 新建且有 generation/ownership 证明的资源，不 down 复用实例或其他 target；bundle 任一文件缺失/漂移零写 store 以外的任何东西；不得以 lane 的 `accepted` 冒充 publish admission，也不得把 integration 工作区的裸 fast-forward push 当作已验收。publish 目标只剩 `origin/dev1.0`：`local_git_cas_publish` 在最终写入前独立重算 admission 自摘要，复验 exact 前驱/签名/有效期、candidate/tree、before/after、规范 linked worktree 与 hub origin push 身份与 remote，且自身检查 ancestry。`QWQ_ACCEPTANCE_PUBLISH=1` 只可作调用标记，不证明 admission；缺证据、仅 env=1 或错身份即零写。这些零写约束由本地 accept/bundle/integrate/hook 执行，不代表服务端拒绝任意普通凭据 FF。dev 旧 `04. Lane Gate` required check 按授权撤除，专用 publisher/broker 与 hosted 资格验真保持 OPEN-004 `track`，不作为日常本地合入或可达 dev 的远端 lane 删除前置；dev 禁删/禁 non-FF 与 main promotion 强制不变。
- 测试 seam：绑定 daily GWT-006/GWT-007 与 local CI GWT-008，以真实 Git 合并、不同候选同 parent CAS、来源冻结后的 lane 前移、同 tree 新 commit、Gamma 远端漂移及显式/自动 owner 漂移负例验真；预检拒绝时证明 HEAD/index/WIP 不变，单 lane 原样 FF 环境调用为零。既有 integration-run、environment-scheduler、handoff consumer 与 release-runtime local contract 保留 mode 互斥、Beta opt-in、bundle round-trip 和漂移拒绝。最小输入设计还须证明单 exact Ops handoff 唯一解析同 release attestation，直接 producer JSON/歧义 artifact/错摘要拒绝；恢复基线来自成功记录、首次缺基线需显式输入、正常内容更新拒绝同 candidate 伪 rollback，内容 unchanged 正例不生成新 release。通过可控 producer/consumer 身份验证跨工作树成功和两侧独立漂移失败，不能关闭 currentness；构建调用计数证明同产品一次、不同架构/编译输入不误复用。实际 Alpha 报告必须证明 healthy+UAT failed、cleanup failed 仍阻断，原始报告和既有 bundle refs 可独立追溯到同一候选，summary 三层不复制 authority。上述新增行为尚缺实现与真实执行证据，分别由 daily-merge OPEN-006/009 承接，不以设计存在声明已接线。
- 理由：采用 CI/CD 的一次构建、按不可变产品晋级与执行前冻结恢复基线，使操作者只选择业务交接而不是重复填写同一 release 的多个定位参数；质量只生产一次、证据只引用一次，仍区分内容生产、环境消费与源码发布的 authority。沿用现有入口和事实，不引入过渡双轨；同一 immutable 内容可服务多个有效源码候选，但当前环境验收必须独立成立。Beta opt-in 保留原政策，不能被输入精简或证据复用降格。
- 被否决方案：在 integration 工作区消费 handoff 时关闭 `validate_current`（放宽 Data 准入合同）；在 integration 重算 candidate/ImpactPlan 再比对 digest（candidateId 不可重建，重算只是第二真相源）；把他方 lane 的 `.qwq_output` 证据字节整目录复制到 integration 工作区（伪装 delivery identity，且无 manifest 绑定）；无验真 admission 的 lane 直推、外来 clone 或非规范 hub/origin 发布、同一 candidate 出现第二个并发 publisher（绕开唯一带资格通道）；把发布座位继续绑定在 `integration/` 目录上（座位不是资格，只增加换工作区停点）；沿用 `IMPACT_PLAN.NO_LIVE_ENVIRONMENT_REQUIRED` 表示「政策跳过 Beta」（原因码失真）；在 Gamma 与 prod canary 之外再加任何第三级集成验证环境（与两级结构冲突）。

### DEC-015 host-target 单运行权威与全执行期 fence

- 对象与 owner：沿用部署控制面的 host-scoped 运行权威扩展 target slot，而非新增 coordinator。host/container-daemon 身份与受管根须一致，跨 worktree/用户不得自设锁根绕过；worktree 仅保存来源和报告引用。运行 generation 独立于 candidate pointer，package 仅产候选，不能自动替换 running；每 target 一套拓扑可包含多个进程，test-live/immutable candidate 不能并存为两套。
- Command/query：只读 discovery/status/lease 查询不删除 stale 状态；start 相同 runtime/config identity single-flight，唯一 creator 产出后其余 attach，重复 attach 不 build/up、不清数据、不切内容。不同 identity 返回 typed conflict；显式更新须 target 独占 mutation、generation 比较与 consumer 协调，内容激活另用短 CAS。准出前驱顺序只约束事实，不限制其他健康 target 持续运行。
- 执行权：scheduler 选中/去重/create-once 不授予执行权，必须原子 claim 同 target execution slot。唯一 executor 持 fence 贯穿全部有副作用子进程；父进程退出后旧子进程未终止或可靠隔离不得接管。superseded 只说明资格失效，不能当 cleanup 已完成。
- hosted 唯一authority位置：`prod-hosted` 的 target execution slot 固定归 `access-isolation.yaml` 当前 `management.defaultHostId` 上的 service-plane账号，存于该账号既有 `composeProjectRoot/release-ledger` 持久控制目录，由现有 `hosted_release_ledger_lib` 在同一 ledger lock 下追加 execution generation、owner attempt、inventory digest、expected release generation、参与placement与执行收口记录。它是既有execution-slot的hosted实现，不建另一个registry、业务发布状态机或第二锁根；release generation仍表示发布事实，execution generation只保护执行权，不能相互代替。authority host搬迁必须先完成显式受控移交及全量history/readback，不自动选主；单机和多机都只向这一authority申请，同target多控制端不得各自在本机缓存授予执行权。
- 权限与实际effect绑定：控制端保留各plane现有独立SSH凭据，只能经受管入口申请中央slot，再以对应plane身份启动固定的受限execution guard；service authority不持有edge/media/data/ops/root密钥、不跨账号执行。中央先持久化本attempt的完整inventory与逐placement执行单（动作闭集、expected identity、材料/路由/资源摘要、单调步骤序号），再由控制端通过现有认证SSH投递给对应guard。guard不因caller token或`VerifyHeld`返回值启动：必须比对通过受信控制端会话交付、已登记的exact执行单，原子消费本地该generation/步骤，取得该plane的既有运行控制目录独占锁，并由同一guard实际启动/监督子进程、记录进程启动身份与退出结果。中央未登记步骤不得投递，guard ACK前不得宣称已覆盖；受限入口必须禁止绕过guard的原tar/systemctl变更通道。多次投递只返回同一执行结果，不重复effect；跨plane写入权限不扩大。执行单投递者属于现有受信deployment controller，用户CLI自行拼字段不属于可信投递；该可信会话安装/限制尚未具备时阻断，不以本地fixture作authority。
- acquire顺序与部分失败：中央以expected execution/release generation原子保留唯一slot，随后按canonical inventory的hostId、plane、instance、replicaId字典序获取所有参与guard；每个target使用独立slot，健康的其他target可并行，共享端口/物理容量另遵守host资源门。完全取得前只允许受管prepare/只读，不改变可见配置、路由或启动candidate；任一host/plane不可达、重复身份、endpoint不符或锁失败均不产生完整观察。已取得guard按逆序显式收口，中央仅在全部退出/无在途effect可证时释放slot；释放ACK未知留下执行阻断记录，不能因“还没放量”推定零effect。多host部分成功不是target成功，不降级为单host或缩小expected集合。
- writer覆盖选择：`sync_prod_plane_stack.sh` 写入active/current配置、Caddyfile、unit或其引用目录的tar属于受保护mutation，须在guard内部按exact执行单落盘；只有不可被运行时发现、不可修改active指针、按digest/attempt私有且不覆盖既有字节的staging上传可在slot外进行，提升staging到运行投影必须持slot。`deploy_to_prod.sh` 的candidate启动、stable路由切换、gray停用与观测配置切换均消费同一slot并交guard执行；`config_release_apply_stage.sh` 仅算SLO、不写路由，不另申请执行权。ledger activation/stage/recovery CAS在同一authority核对execution owner及expected release generation，旧owner即使仍能发SSH请求也不能追加成功事实；只读ledger fetch不初始化目录，更不签absence。任何新增mutation入口必须归入此列表，否则producer判writer覆盖不完整。
- systemd与正常重启：生成的unit启动固定guard入口，而非直接对可变工作目录运行compose。已准入runtime/config/image/route全为exact不可变身份的正常重启只复用本地已登记运行身份，不要求获取发布slot、不改变execution/release generation，不能被观察长锁永久阻塞；它仍须通过本地运行身份核验，不可读取后来被tar覆盖的同名配置。改变unit定义、材料、配置、监听/路由或启停candidate是mutation，必须有中央步骤及本地guard。absence观察若存在已准入运行身份或可自动重启的已启用unit，即拒绝无active结论；有prior的只读健康观察如遇重启/运行漂移也只记不稳定，不把业务可用性当配置切换。OS/root可绕过的操作不被此设计声称绝对禁止，其造成的runtime drift必须阻断取证与准入。
- prevalidate/distribution覆盖：prevalidate读取或改动同target共享入口、固定发布端口、unit、媒体挂载或执行回收时，必须使用同一中央slot；真正完全隔离且不可被正式runtime发现的私有staging不竞争slot，但其启动/发布口仍由inventory与host资源门裁定，不能仅凭名称叫prevalidate就豁免。distribution上传不可变且未被current指针引用的文件可在slot外；Web current/CDN公开选择器、App下载入口或服务所依赖Web物料指针的切换须进入同一target slot。纯移动商店渠道动作若不改变该target的任何取证事实则保持原独立分发authority，不纳入服务发布锁，也不能反向签target absence；跨scope交叉影响无法证明时拒绝并要求完整参与者声明。
- 控制端断开与孤立子进程：execution guard是目标host/plane账号的受管长驻监督进程，SSH仅提交/查询，SSH断开不使guard子进程脱管，也不清除中央owner。guard持锁贯穿受保护读/写及其后代进程；PID单值、连接关闭、TTL到期或controller退出均不能证明执行结束。guard崩溃/重启发现未终结执行记录时进入reconcile-only，在证明同启动身份的进程组/cgroup已退出或经额外授权可靠隔离、且实际effect已readback前拒绝新generation；本地flock因进程死亡释放也不得绕过durable未终结记录。authority断开时guard不再接收新步骤，已启动步骤按原授权执行到可读回结果；无法收口即unknown，禁止中央超时抢占。
- 观察至Human consume/CAS交接：先以只读观察意图保留execution slot并取得全部guard，再在其保护下读取已有ledger/history、完整inventory、全部入口路由和在途执行记录；slot预约只是execution协调事实，必须与被观察发布历史分开，不能创建缺失的release state/receipt后称其原为空。缺已登记控制目录/历史根/路由owner或权限时直接unknown。观察结果绑定既有history、execution generation、expected release generation、inventory、每个guard incarnation/步骤和真实时间窗口；只在所有保护仍连续有效且没有runtime drift时可用于后继。等待Human期间可以继续持同一slot且不改变配置；若选择释放，观察立即失去交接资格，重新取证并重新绑定Human fingerprint。consume后的winner command必须在中央同一slot所有者下以expected execution/release generation转换为activation执行单，而非释放再抢锁；消费结果丢失先查exact Human winner，中央CAS结果丢失先查该attempt，任一unknown保持冻结，不重复消费。该handoff接口必须完成后才解除absent硬拒绝，当前设计本身不产生authority。
- hosted状态与取证边界：结果区分observer完整但non-admission、authority不可达、participant不可达、执行权冲突、失锁/guard incarnation漂移、在途结果未知与runtime drift，均使用后续canonical typed契约表达；只有完整读回不代表可部署。信任边界限于受管controller、限制过的plane入口、已登记guard与真实OS/SSH身份；不承诺检测所有未受管root动作。无新的host、DB或跨plane特权为方案前置，使用既有service authority主机、平面账号与本地持久文件；安装受限helper/user systemd及收紧现有登录执行面属于后续显式环境变更，未经授权/读回前保持不可用，不把代码实现授权当生产安装授权。
- 设备与租约：设备绑定按 device + application identity 独占，跨设备可共用 nonprod；每 attach 有独立 nonce、exact lease 与运行 generation，原子 acquire/bind/release 比较完整身份。direct 安全租约不签更高 authority，Alpha 离线只需设备绑定。旧退出、PID 复用、TTL 到期或本 worktree receipt 缺席均不能释放新代；跨环境切换由启动 owner 重建 scope。
- 资源与容量：生命周期锁按 target，Docker/VM 管理和全局 GC 保留独立 host 锁。CPU/RAM/VM 配额、磁盘与构建峰值独立原子预约，配额不足只拒绝/排队新任务，绝不驱逐已有环境。构建只锁 SDK 所需私有输出，不覆盖共享 generated config；只读 exact digest 可共享，GC 尊重所有引用。
- 失败恢复：created/reused ownership 自准备起保持可追溯，失败只清理本次 created，保留复用服务/证书/转发/数据；matrix 禁止全 target pre-down。退出或最后 consumer 释放不自动 down。stop/restart/repair 必须证明 generation、ownership 与 lease 已协调，不能凭端口/PID/进程名回收；不明执行权保持阻断，恢复走同一控制面显式 reconcile。
- 理由：运行代际、候选、执行权与使用租约解决不同竞态；统一 host-target 权威可同时满足单例与跨环境并行，容量不足无需粗暴停止其他环境。
- 被否决方案：全局运行串行、每 worktree 一套锁/receipt 权威、启动隐式替换、package 切运行指针、执行前一次性 fence、TTL/PID 判停、last-client down、matrix 全环境预清理、资源不足驱逐旧环境。
- SLI/SLO 与测试 seam：单 target 重复运行数及未授权资源变更数目标为零，记录创建/复用/冲突、lease stale/释放、fence 拒绝、预算排队与恢复时长；target/env 可作有限维度，设备/PID/generation 只进脱敏日志/trace。local_contract 用 barrier、可控子进程和时钟注入并发 scheduler/旧 lease/ABA/预算不足；api_integration 跨 worktree 同 daemon 验证单 creator、父崩溃接管与 owned cleanup；设备 UAT 持续读取证明另一环境失败无干扰。生产跨主机 HA 仍归网络 owner OPEN，不从本地实验推定。
- hosted测试seam与最小实现：复用 `hosted_release_ledger_lib/{contract,request_validation,ledger_store,actions}.py` 的持久字节、锁、CAS与history，在其内扩展target execution-slot，不新增通用锁库；`repair_runtime_recovery.py::_prod_release_lock` 退为本机排队而非authority，`deploy_domain.py`、`deploy_rollout.py`、`deploy_prod_finalize.py`、`deploy_release_state.py`、`sync_prod_plane_stack.sh`、`deploy_to_prod.sh` 和 `prevalidate_prod_hosted.py` 统一进入受限执行单路径，`render_prod_plane_stack_lib/runtime_outputs.py` 生成guard包装unit，`inspect_prod_plane_runtime.py` / `inspect_surface.py` 读取guard保护中的真实runtime，`official_distribution_release.py` 的可见指针切换接入同slot。确需新增的是每plane的受限命令执行/子进程监督adapter及中央slot的受信投递/回读接缝，不是第二registry；具体authoring字段/安装路径与动作白名单须由现有contracts/access-isolation owner先冻结。local_contract使用真实flock、子进程barrier和临时持久目录证明：两个controller同target只能一个winner、观察中配置tar/路由writer拒绝、不同target不互锁、同identity健康重启不阻塞、任一plane缺失/重复host/错误endpoint拒绝、父断连/guard崩溃后旧子进程存活不得接管、锁丢失或读超时不能完整取证、部分prepare逆序收口及lost ACK不释放、observe→Human consume→activation同owner CAS无空窗；不得用空callback或自述held代替真实执行。api_integration另需真实host/plane授权安装与隔离失败演练，代码测试不能证明外部已覆盖。

## 5. 失败与恢复

- 失败类型：分支 policy 无效、PR/ref 非法、`main` direct push、integration push 缺 before/after OID或 ancestry authority、integration/backsync 非 fast-forward、force/delete、ref compare-and-swap 冲突、Prod source 不可达 main、权限拒绝、依赖超时、候选摘要冲突、证据缺失或持久化失败。
- 可见结果：调用方收到稳定 `OPS.BRANCH.*` 或父能力 canonical failure；任何失败均不写 promotion、candidate、backsync、deploy 或 rollback 成功事实。
- 恢复动作：非法 PR/ref 修正 head/base 后重试。backsync equal 幂等完成，安全 ancestor 可重读后重试。`dev1.0` 分叉时停止并要求人工裁决，不创建临时分支或 force。push 返回成功但 readback 未知时禁止盲重试，先从权威 ref 回读。after 等于 promotion OID 时收口成功，after 仍等于 before 时可安全重试，其他值冻结 eligibility。远端权限、网络、ancestry 或 hosted authority 不可确认时停止并保留 before/after readback。
- 禁止 fallback：不得回退到 Mock、旧 wire、双读双写或页面本地写副本。
- factory/CMM/Prod 恢复：exact-byte 校验、签名/attestation、配置闭包、hosted readback 或 predecessor 失败时保持零 production/distribution mutation；修复 authority 或生产下一 RC 后以新 command 重试，不改写原 fact。stage 失败按 `DEC-008` 的 prior 存在性处理：present 只可按 exact previous released terminal 与 rollback readiness 回滚，absent 只可按已授权恢复证据回到未激活安全态；attempt outcome 未知时先 hosted readback，同一 outcome 幂等收口，确认失败后新建 attempt，禁止覆盖旧 attempt。
- 外部阻断：生产主机、凭据、审批、Provider、真实设备、渠道审核或 hosted authority 不可用时保留 typed blocker 与最后可证明的 exact ref；prevalidate、prod-sim、历史 snapshot、Actions success 或旧 receipt 都不得包装为正式 Prod/渠道成功。

## 6. 质量与观测

- 分支治理由 Platform Ops owner 记录 `branch_policy_decision_total{event,status,reasonCode}`、`branch_backsync_terminal_seconds{status}`、`branch_ref_readback_complete_total{ref,status}` 与 `branch_release_eligibility_total{status,reasonCode}`；每条 attempt 绑定 repository、run/attempt、promotion SHA、before/after OID 和 evidence digest，脱敏 receipts 保留至少 90 天。
- 每个 policy/admission attempt 的 reason 覆盖率与 ref readback 完整率目标为 100%。成功 promotion 后 backsync 在 300 秒内进入 success、idempotent 或 blocked 终态的月度目标为 99%。任一无 reason decision、readback 缺失、`main/dev1.0` 分叉、未授权 main source 取得 eligibility 或 backsync 超过 300 秒立即触发 Platform Ops P1 告警。外部 GitHub 不可用时保持 fail-closed，不用 availability 降级换取放行。
- `prod-hosted` 的正式灰度 workflow 必须人工 dispatch 并保留 approval；在 Provider、SFU、真实数据、观测、灾备或回滚证据缺失时只允许不可提升 prevalidate，且 post-deploy probe 置信度仍须单独验收。
- 运行装配从各服务 `environments/<env>/deploy`、Ops 同名环境入口和真实 Compose/Kustomize 扫描推导；本地端口保留 `local_env_port_manifest`，prod rollout 保留 `gray_rollout_stages`，服务配置由自治 package 的 provenance 摘要证明。
- 每个 Prod rollout stage 必须执行 `stackctl health + inspect + doctor + integration probes + slo gate`；任一失败写入 GATE_BLOCK/rollback 证据，不得由 workflow 合成成功。
- factory/CMM/activation/stage/terminal/soak 观测必须记录 exact predecessor digest、authority、run/attempt、stage、decision、typed reason 与 hosted readback 摘要；required actual-byte/readback 与 reason 覆盖率目标均为 100%，缺任一项立即阻断。stage health/SLO 阈值只消费 canonical rollout policy，不在 workflow scalar 或本设计复制；真实 Prod 外部阻断与 rollback 不计作 passed 样本，也不得提升 release/distribution 状态。
- App 构建耗时必须读取 Android nonprod/prod、iOS nonprod/prod 与 Web shared 五个实际 Jobs API 节点并取最大值。任何 shard 缺失时 timing gate 失败，不允许回退到 static/serial 近似值。
- 独立可观测：每域 `service.name` + 指标维度独立，使“逻辑独立”在合并部署时依然成立，并为拆分提供数据依据。
