# L3 Story：模型属性的取值语义只来自显式声明 (`model-attribute-semantics`)

> 所属能力：[`system-architecture-and-engineering-guide`](../spec.md)
>
> Journey / Scenario：不直接拥有用户 Journey，但本能力的判否会收缩用户可见路径，因此 `REQ-005` 承载被收缩路径的终态与恢复动作要求
>
> 设计归属：[L2 DEC-030](../design.md#dec-030)

## 1. 用户价值

作为消费领域模型属性的开发者，我希望每个决定行为的属性取值都能回答「这是谁在哪个契约里声明的取值」，从而让「数据还没到」不会被当成「这是公开圈子」、「服务端新增的状态值」不会被当成「可以打开」、「契约里根本不存在的取值」不会留在判定分支里。作为用户，我希望这些判否收缩掉的路径都给我一个说明原因的终态和一个能点的下一步，而不是把我留在一张没有按钮的卡片上。

## 2. 范围与非目标

### In Scope

- 契约声明为闭集的属性，在其每条消费管线上保持类型化，判定读 typed 常量。
- 四种输入形态各自独立判定：闭集零值、宿主对象缺席、闭集外入站取值、契约未声明的取值。
- 一个业务语义只有一个可写载体，派生方向单一。
- 默认值只在写侧一次性物化，读侧只翻译不发明；测试替身同受此约束。
- 本能力判否导致的用户可见收缩，其终态、恢复动作与文案归属。

### Out of Scope

- 配置装配面的判定语义来源，归 [`explicit-semantics-no-implicit-inference`](../explicit-semantics-no-implicit-inference/spec.md) 与 [DEC-029](../design.md#dec-029)。本 Story 拥有的是模型属性面，两者共用「判定只读显式声明」这一句判据，但声明位不同：那边是 config schema 键与 env 键，这边是对象契约的字段与枚举成员。
- 单个返回值的结果状态形态（在场有值 / 在场为空 / 缺席 / 失败），归 [`absent-empty-failure-nullability`](../absent-empty-failure-nullability/spec.md) 与 [DEC-025](../design.md#dec-025)。本 Story 管「属性取值凭什么进入判定分支」，那边管「一次返回怎么表达它的结果状态」。
- 删除语义的三层 owner 与 tombstone 保留期，归 [DEC-007](../design.md#dec-007)。本 Story 只要求删除态不被第二个载体独立表达。
- 读投影的值域可以宽于写侧闭集这一既有裁决，归 [DEC-014](../design.md#dec-014)；本 Story 不收窄它，只要求宽出来的取值同样是显式声明的成员。
- 全仓存量整改的完成度不属本 Story 的准出条件，按 `OPEN-001`、`OPEN-002`、`OPEN-003` 分别承载。

## 3. 行为要求

<a id="req-001"></a>
### REQ-001 闭集属性在每条消费管线上保持类型化

- 契约以 `type: enum` 加 `enum_ref` 声明的属性，在服务侧领域模型、跨对象读端口的 slice、投影行与端侧模型上都必须是该闭集的类型，不得退化为裸字符串。
- 判定必须与该类型的具名常量比较，不得与字符串字面量比较。
- 不得以大小写不敏感比较放宽闭集值域：闭集成员的 wire 取值是精确值，`Deleted` 与 `deleted` 不是同一个声明。
- 同一属性在同一条管线的两端不得一端类型化、另一端裸字符串；类型化在跨越进程与语言边界时由各自的生成物承担，不由消费点自行解析。

<a id="req-002"></a>
### REQ-002 四种输入形态各自独立判定，不得合并为「缺席」

- **闭集零值不是合法取值。** 契约声明 `NOT_NULL` 的枚举属性，其语言零值（Go 的 `""`、Dart 的空串）不在闭集内，判定必须按不合法处理，不得为零值单独开一条放行分支。
- **宿主对象缺席时不产出属性级判定。** 属性所属的聚合或读模型对象整体不在场时，不得取该属性的默认值继续判定；此时唯一合法的结论是「尚无判定依据」，由调用方按加载态或失败态处理。
- **闭集外入站取值必须落到显式声明的未知成员。** 入站方向收到闭集未声明的取值时，必须映射到一个显式声明的未知成员，且该成员不得等价于任何放行态；不得映射到闭集中语义最宽松的成员。
- **契约未声明的取值不得出现在判定分支里。** 代码不得判定一个该属性契约闭集中不存在的取值；这类分支是死分支，必须删除而不是保留为兼容。

<a id="req-003"></a>
### REQ-003 一个业务语义只有一个可写载体

- 同一业务语义不得由多个可独立写入的属性共同表达；判定不得把两个载体用逻辑或合并，因为那让任一载体单独失真都不可见。
- 已存在伴随载体时，派生方向必须单一：权威载体写入后由同一次事务派生伴随载体，伴随载体不得被独立写入，也不得反向决定权威载体。
- 读侧不得把多个权威取值塌陷成一个展示取值后丢失区别；需要归并展示时，归并结果必须是显式声明的展示态成员，且不得让语义相反的两个取值归并到同一个成员。

<a id="req-004"></a>
### REQ-004 默认值只在写侧物化，读侧只翻译不发明

- 属性默认值的声明位唯一。默认值在写入时一次性物化为该属性的显式取值，物化之后它与任何其他显式取值不可区分。
- 读侧不得为缺席或零值的属性填入默认值：读侧填默认会制造一个写侧从未声明过的取值，且该取值无法指回任何一处声明。
- 测试替身受同一约束。替身不得为被测属性填入默认值，否则断言绿在替身的默认值上而不是被测规则上，而这种假绿在替身与被测代码同时演进时不产生任何信号。

<a id="req-005"></a>
### REQ-005 判否收缩的用户可见路径必须有显式终态与恢复动作

- 因本能力判否而不再放行的用户可见路径，必须有一个说明原因的终态，并带重试或安全返回中至少一个恢复动作；不得静默消失、空白，也不得落到没有任何动作的展示卡片上。
- 宿主对象缺席期间的渲染态与「加载已结束但对象仍缺席」的终态是两个不同的终态，必须分别可达；后者不得依赖失败对象在场才成立。
- 闭集外入站取值的终态文案不得复用断言性措辞。把「本端未声明该取值」说成「内容已被删除」会把版本落后谎报为内容变化，使用户去找作者而不是更新客户端。
- 终态文案只能来自既有文案常量或 l10n，不得在渲染层新写字面量。

## 5. 验收场景

<a id="gwt-001"></a>
### GWT-001 闭集零值不放行，判否与不合法取值同路

- GIVEN 一个 `status` 为语言零值的 Conversation，操作者是其活跃成员。
- WHEN 经 `MemberService` 的导出成员命令与 `ConversationService.UpdateSettings` 请求该会话。
- THEN 每条命令都判否，结论与 `status` 取 `dissolved` 时同路，不因零值获得放行。<!-- gwt-001.t1 -->
- AND 判否不依赖调用点各自补写零值分支：授权门只有一处，零值在该处即被判为不合法。<!-- gwt-001.t2 -->
- AND 会话创建路径写入的 `active` 是该闭集的具名常量，不是字符串字面量。<!-- gwt-001.t3 -->

<a id="gwt-002"></a>
### GWT-002 宿主对象缺席不产出可访问性判定，缺席终态带恢复动作

- GIVEN 圈子详情对象缺席，分别处于「仍在加载」与「加载已结束并置了失败对象」两种状态。
- WHEN 渲染圈子壳层。
- THEN 两种状态都不渲染以圈子属性为输入的可访问性拦截。<!-- gwt-002.t1 -->
- AND 「仍在加载」渲染加载态而不是权限拦截。<!-- gwt-002.t2 -->
- AND 缺席终态带至少一个可点的恢复动作，不落到无动作的展示卡片。<!-- gwt-002.t3 -->
- AND 详情对象在场时，可访问性判定读的是该对象声明的可见性取值，不是任何默认值。<!-- gwt-002.t4 -->

<a id="gwt-003"></a>
### GWT-003 闭集外入站取值落到显式未知成员且不可打开

- GIVEN 分享目标可用性收到闭集未声明的取值，以及该属性整体缺席。
- WHEN 经公开工厂构造分享互动条目，不经测试替身补值。
- THEN 两种输入都落到显式声明的未知成员，不落到可打开态。<!-- gwt-003.t1 -->
- AND 该条目不可打开，行不可点，预览呈现不可用。<!-- gwt-003.t2 -->
- AND 未知成员的文案说明「本端未声明该取值」并指向更新客户端，不复用已删除、私密或审核中的措辞。<!-- gwt-003.t3 -->
- AND 该属性的可用性判定为穷尽匹配：新增闭集成员时未处理该成员的判定点编译失败。<!-- gwt-003.t4 -->

<a id="gwt-004"></a>
### GWT-004 契约未声明的取值不进入判定，多载体不以逻辑或合并

- GIVEN Post 的可用性投影，其 `status` 闭集为 `pending_review`、`published`、`rejected`、`deleted`。
- WHEN 计算目标可用性。
- THEN 判定分支中不存在该闭集未声明的取值。<!-- gwt-004.t1 -->
- AND 删除态只由权威载体判定，不与删除时间戳用逻辑或合并。<!-- gwt-004.t2 -->
- AND `rejected` 与 `pending_review` 不归并到同一个展示成员：已拒绝不呈现为审核中。<!-- gwt-004.t3 -->
- AND 该投影属性在契约上声明为闭集，端侧消费该闭集的生成物而非手写枚举。<!-- gwt-004.t4 -->

<a id="gwt-005"></a>
### GWT-005 门禁对新增违规变红且对既有合规不误报

- GIVEN 测试树内的合规与违规契约样本各一组。
- WHEN 运行模型属性语义门禁。
- THEN 违规样本使门禁判否，判否文本指名属性与缺失的声明。<!-- gwt-005.t1 -->
- AND 合规样本不产生误报，包括「缺席即无引用」「游标空即无更多数据」这类缺席本义的声明。<!-- gwt-005.t2 -->
- AND 门禁不依赖豁免名单或存量基线文件成立。<!-- gwt-005.t3 -->

## 7. 开放事项

<a id="open-001"></a>
### OPEN-001 闭集属性的类型化在服务侧只有一个服务成立

- 类型：`capability_gap`
- 优先级：`P1`
- 准出影响：`track`
- 影响或价值：缺的不是生成能力而是逐服务开启后的消费点收敛。服务侧 typed enum 生成能力已存在（`internal/metadata/codegen/domain_generator.go` 的 typed enum 选项），但全仓只有 circle 一个服务的生成器调用它，其余服务的枚举属性在领域模型上仍是裸字符串。因此 `REQ-001` 目前只在已开启该选项的服务上成立，其他服务的同类属性仍可用字面量比较且不会被任何检查拦住。开启会让该服务全部裸字符串消费点编译失败，需要逐点裁决而不能批量替换。
- 前置事实：开启前必须先收敛契约的 authoring 形态。`services/content-service/contracts/content/post/fields.yaml` 有 5 个字段同时写着 `enum_ref` 与 `type: string`，而同一对象内紧邻字段用的是 `type: enum`。生成器只认后者（`domain_generator.go` 判 `field.Type == "enum" && field.EnumRef != ""`），因此这种并存会在开启选项时把同一个语义生成为一个 typed 载体加一个裸字符串载体，正是 `REQ-003` 禁止的形态。这 5 处属于不生成 Go 结构体的写侧请求对象，单独收敛没有运行期效果却会改变 ContractGraph 摘要并触发一次跟端契约交接，因此它与开启选项属于同一次同源变更，不拆开做。
- 完成判定：全部服务的生成器均开启 typed enum，同一枚举在同一份契约内只有一种声明形态，且 `GWT-004` 的 `gwt-004.t4` 在每个服务的枚举属性上成立。

<a id="open-002"></a>
### OPEN-002 闭集外取值的未知成员缺少可声明形态

- 类型：`capability_gap`
- 优先级：`P1`
- 准出影响：`track`
- 影响或价值：无法在共享闭集上声明未知成员及其 wire 语义。`REQ-002` 要求闭集外入站取值落到显式未知成员，但共享闭集当前以简写列表声明（`contracts/metadata/_shared/types.yaml`），该形态只能写成员名，无法为某个成员声明其 wire 取值。因此「未知」这个成员无法表达「它对应的 wire 取值是闭集之外的任何值」这一语义。服务内的枚举声明已有长格式可承载（`services/assistant-service/contracts/_shared/enums.yaml` 以 `wire: ''` 表达过同类需求），共享闭集尚未裁决是否统一到长格式。
- 完成判定：共享闭集具备声明未知成员及其 wire 语义的形态，且 `GWT-003` 的 `gwt-003.t1` 在共享闭集属性上成立。

<a id="open-004"></a>
### OPEN-004 本能力没有全仓静态门禁，判据仍靠人工评审加逐点棘轮

- 类型：`capability_gap`
- 优先级：`P1`
- 准出影响：`track`
- 影响或价值：当前只有已整改点的 `local_contract` 棘轮，`REQ-001` 到 `REQ-004` 没有任何全仓静态检查兜住。已整改的 chat 会话状态由源码扫描断言锁定（`conversation_status_closed_set__contract__local_contract_test.go`），圈子详情缺席由 widget 断言锁定，两者都不会重现；但同类形态可以在任何新代码、新服务里第一次出现而不被拦。门禁判据必须先收窄：本能力的四种输入形态中，「闭集零值豁免」与「契约外取值」可由「闭集属性的比较对象是否为该闭集成员」判定，而「宿主对象缺席」与「读侧填默认」在语法上与大量合法的空值判断同形。契约里「为空表示 X」的声明也存在三类——分页游标的终止信号、可选引用的缺席本义、被缺席承载的业务状态——只判文本形态会对前两类产出压倒性误报并很快被绕过。
- 完成判定：`GWT-005` 的三条结果子句（`gwt-005.t1`、`gwt-005.t2`、`gwt-005.t3`）具备门禁自证 `local_contract` 的子句级绑定证据——门禁对新增违规样本变红、对既有合规样本不误报，且不依赖豁免名单或存量基线文件成立。

<a id="open-003"></a>
### OPEN-003 多载体与默认值多轨的存量未逐处裁决

- 类型：`capability_gap`
- 优先级：`P2`
- 准出影响：`track`
- 影响或价值：尚未逐处裁决存量的多载体与默认值形态。`REQ-003` 与 `REQ-004` 的判据成立，但存量仍未收敛。多载体方面，删除语义在多个对象上同时由状态取值与时间戳表达，其中一部分由聚合不变量守住、一部分没有。默认值方面，属性默认值当前存在多套 authoring 形态，其中一部分只被端侧生成物消费、一部分由存储层把缺席物化为空值，尚未收敛到「一处声明、写侧一次物化」。逐处裁决需要按属性判断权威载体与派生方向，无法由门禁批量判定。
- 完成判定：存量多载体属性的权威载体与派生方向逐处落契约声明，默认值 authoring 收敛到单一形态，且 `GWT-004` 的 `gwt-004.t2` 在全部删除态属性上成立。
