# L2 Design：结伴与线下相聚协调 (`gathering-coordination`)

> 对应规格：[L2 spec](./spec.md)
>
> 设计触发原因：新增聚合与状态所有权，且跨 circle-community、chat-conversation 与 recommendation-platform 三个领域交接行动承接关系。

## 1. 背景、目标与非目标

- 背景：交集行动阶梯的同行与线下两级没有任何承接对象，发起结伴只能落到裸建群，加入类行动全部不可承接。
- 设计目标：用一个聚合承接同行与线下两级，并让每个字段都有明确消费方。
- 非目标：不拥有消息，不承担实时位置能力，不建立独立的语音房对象。

## 2. Story 协作与状态流

- 状态 owner：Gathering 自身状态与参与者名单由本能力拥有，绑定会话的成员资格与消息由消息域拥有。
- 并发边界：容量判定与名单写入在同一事务内完成，并发申请不得越过容量上限。
- 幂等边界：同一账号对同一 Gathering 的重复申请不产生第二条名单记录。
- 一致性窗口：参与者计数是名单的读取时投影，不作为独立可写事实保存。

## 3. 端云与数据流

- App 责任：从行动提示进入发起与加入入口，展示名单与状态，进入绑定会话。
- Metadata/contract：Gathering 与参与者的字段、状态枚举与错误语义在 circle-service 的服务本地契约定义。
- Service/Data/Ops 责任：circle-service 拥有聚合与名单，chat-service 提供绑定会话的创建与成员同步。
- 缓存或投影：参与者计数与名单摘要是投影，可整体重算。
- 外部依赖：无。

## 4. 关键决策

<a id="dec-001"></a>
### DEC-001 结伴与线下相聚合并为单一 Gathering，用时间区间表达差异

- 决策：以起始时间加可空结束时间的时间区间同时表达「这个周末想去有人一起吗」与「周六下午两点集合」，不引入形态枚举，也不建立第二个聚合。
- 理由：两者的结构完全一致，都是一个发起人加一个目标对象加一个时间表达加一组参与者加一个绑定会话加一个状态。唯一差别是时间确定性，而时间确定性本身就是时间字段能表达的东西。
- 被否决方案：分别建立约伴与线下局两个聚合——两套等价的状态机与名单逻辑，用户还要先回答一个「这算约伴还是线下局」的无意义问题。
- 影响 Story：[`gathering-lifecycle`](./gathering-lifecycle/spec.md)
- 关联要求：`REQ-001`、`REQ-002`
- 关联验收：`SIT-001`

<a id="dec-002"></a>
### DEC-002 Gathering 与 Circle 同构，只持有会话引用而不拥有消息

- 决策：Gathering 持有其群会话的引用，消息、成员资格与通话事实全部归消息域。
- 理由：圈子已经确立了这条边界并已有实现先例。让 Gathering 拥有消息会在消息域之外产生第二份会话事实，撤回、审计与同步都要双写。
- 被否决方案：Gathering 内嵌一段轻量消息流——轻量消息流最终都会需要已读、撤回与同步，也就是重新实现一遍消息域。
- 影响 Story：[`gathering-lifecycle`](./gathering-lifecycle/spec.md) 与 [`gathering-conversation-binding`](./gathering-conversation-binding/spec.md)
- 关联要求：`REQ-003`
- 关联验收：`SIT-001`

<a id="dec-003"></a>
### DEC-003 语音房不建对象，复用绑定会话内既有群通话

- 决策：删除独立的语音房行动键，进入同趣语音房等价于加入 Gathering 后在其绑定会话内发起群通话。
- 理由：群会话已有语音与视频通话入口且已支持多人媒体转发，语音房与它的差别只是入口叙述不同。新建对象会带来第二套成员与生命周期。
- 被否决方案：新建语音房聚合并与 Gathering 关联——两个对象描述同一次聚集，用户需要理解两个概念。
- 影响 Story：[`gathering-conversation-binding`](./gathering-conversation-binding/spec.md)
- 关联要求：`REQ-005`
- 关联验收：`SIT-001`

<a id="dec-004"></a>
### DEC-004 审批状态机镜像圈子成员治理，不发明新状态机

- 决策：参与者的待审批、已加入、已退出与已拒绝复用圈子成员治理的既有语义与流转规则。
- 理由：加入策略、审批与容量在圈子成员治理中已经完整存在并已被验证。复用可以让两处的边界行为天然一致。
- 被否决方案：为 Gathering 设计更简单的两态模型——开放加入与需审批两种策略最终都会要求待审批态，简化只是把它推迟到第二次迭代。
- 影响 Story：[`gathering-participant-roster`](./gathering-participant-roster/spec.md)
- 关联要求：`REQ-004`
- 关联验收：`SIT-002`

## 5. 失败与恢复

- 失败：容量已满、重复加入、发起方在申请期间取消、审批被拒绝、绑定会话创建失败。
- 检测：容量判定在名单写入事务内完成，取消与申请的竞态由聚合状态判定，会话创建失败返回 canonical failure。
- 可见结果：容量已满、已取消与被拒绝是三种可区分终态，不合并为同一条通用失败。
- 恢复：被拒绝或已退出的账号可再次申请，会话创建失败可重试且不产生重复会话。
- 禁止 fallback：不得在容量已满时静默放行，不得在会话创建失败后仍标记为已加入，不得产生半加入状态。

## 6. 质量与观测

- 隐私：目标对象与时间区间对可见范围内的用户公开，参与者名单不向未加入者暴露联系方式。
- 风控：发起频率受频控约束，避免以发起 Gathering 作为批量触达手段。
- 指标：发起量、加入转化率与按 vertical 的分布可观测，用于判断行动阶梯在各垂类上的实际承接效果。
- kill-switch：发起入口可整体关闭，关闭后已存在的 Gathering 仍可加入与结束。

## 7. 迁移与回滚

- 切换顺序：先建立聚合与名单，再绑定会话，最后把发起与加入两个行动从不可承接转为可承接。
- 数据处理：行动键的旧名称经登记的迁移映射一次性收敛，不保留旧值别名，也不做双读。
- 删除的实现：发起结伴落到裸建群的临时路径在聚合落地时删除，不保留为降级路径。
- 回滚条件：出现名单与计数不一致或半加入状态时回滚该步骤，行动键回到不可承接而不是回到裸建群。
