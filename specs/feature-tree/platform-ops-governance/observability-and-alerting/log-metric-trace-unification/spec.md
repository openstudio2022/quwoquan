# L3 Story：日志、指标与追踪统一 (`log-metric-trace-unification`)

> 所属能力：[`observability-and-alerting`](../spec.md)

> Journey / Scenario：横切工程能力；由父 L2 spec 参与 AppRoot Journey。

> 设计归属：[L1 DEC-001](../../design.md#dec-001)

## 1. 用户价值

作为平台运维、安全或审核角色，
我希望以 requestId 和 traceId 关联日志、指标与追踪，同时限制标签基数并脱敏主体数据，
从而获得可审计且可回滚的平台治理结果。

## 2. 范围与非目标

### In Scope

- “日志、指标与追踪统一”的输入、可观察主路径、失败语义以及与父能力的交接。

### Out of Scope

- 父能力中由其他 Story 独立拥有的行为、能力级架构决定和实现任务。

## 3. 行为要求

<a id="req-001"></a>
### REQ-001 日志、指标与追踪统一

- 以 requestId 和 traceId 关联日志、指标与追踪，同时限制标签基数并脱敏主体数据。

<a id="req-002"></a>
### REQ-002 契约声明的指标名是逻辑 join key，不承诺存在同名时间序列

- operation 契约里的指标声明名是契约层逻辑标识，用于把契约事实与告警规则、看板和值班口径关联；它不承诺运行时注册了同名时间序列。
- 真实可查询的时间序列由运行时中间件统一注册，具备 SLO 所需的形状；绝大多数声明名在运行时没有对应序列，只作为规则标签值出现。
- 声明名只能出现在告警与看板的标签位置，不得出现在 PromQL 的序列名位置；出现在序列位置即为错误引用并被门禁阻断。
- 声明名可被同一族多个 operation 共享作为分组键，因此与 operation 全限定名不是一一对应，二者在同一条规则上并存是有意设计。
- 因为声明名由人工维护，重命名或拆分 operation 时必须同步复核其声明名归属，不得让分组键继续指向已消失的语义族。
- 端侧埋点、云侧契约与告警规则三处真正的连接键是 operation 全限定名，它在三处必须逐字一致；指标声明名只是该键的多对一投影，把两者当作同一标识的大小写变体是错误模型，据此建立的等价关系一定漂移。
- 端侧 operation 标识有两个互不相干的取值域：一是生成客户端持有的云 operation 全限定名，必须是契约图声明集合的子集；二是没有云侧对应物的 App 本地动作标识。
- 本地动作标识必须落在保留命名空间内，或已登记进云侧摄入的受限词表，且任何情况下都不得与云 operation 全限定名相等；未满足时云侧会把该取值静默折成兜底值，端上埋点与云上指标当场失去同源性。

<a id="req-003"></a>
### REQ-003 契约声明的 p95 延迟目标与指标名同裁决，并与入站超时预算成约束关系

- operation 契约里的 p95 延迟目标与指标声明名适用同一裁决，它是契约层逻辑标识，用于把契约事实关联到告警规则、看板与值班口径，不承诺运行时存在同名告警序列。
- 该延迟目标与同一 operation 的入站超时预算不是可以各自漂移的两个独立数值，二者关系由「超时预算不小于 p95 延迟目标」这一条约束表达。
- 违反该约束意味着契约在声明正常延迟就会触发超时，属于契约缺陷，必须修正契约声明而不是在运行时放宽预算。

<a id="req-004"></a>
### REQ-004 手写 PromQL 必须收敛为「契约派生」与「显式 overlay」两类，且两类都受漂移检测

- 告警与看板规则只允许两种来源：由契约图派生并做字节级漂移检测的生成物，或在 overlay 清单中逐条登记「为何不可派生」的手写规则；未登记的手写规则一律阻断。
- 可派生判定必须是机械的，不接受 allowlist：只消费契约派生的标准请求与延迟序列、错误维度限定在契约声明的错误预算维度、形状对应契约声明的可用率或 p95 目标，且 selector 能解析到至少一个真实 operation。
- 已满足可派生判定的规则必须迁到派生产物，继续留在 overlay 即阻断；反向地，selector 指向契约内服务却匹配不到任何 operation 的规则是死告警，同样阻断，不得用 overlay 理由掩盖。
- 尚未商用的 operation 与已商用 operation 必须取得同形状的派生告警口径，否则它们只能长期靠手写规则兜底，而手写规则正是漂移的来源。

<a id="req-005"></a>
### REQ-005 operation 声明的隐私密级派生到端云两侧运行时脱敏，不另建第二条强制链

- operation 契约声明的数据密级与日志载荷策略必须经同一 codegen 链同时派生为云侧与端侧的运行时策略表，两侧消费同一份派生结果，不得任一侧另写一份策略。
- 运行时脱敏对未登记 operation 必须 fail-closed，按最高密级与最严日志策略处理；静默放行未登记 operation 等于把「契约没覆盖到」变成运行时泄漏。
- 日志载荷策略决定值能否落盘，密级决定哪些值必须掩码、哪些键必须整条丢弃；最高密级无论日志策略如何都整条丢弃，因为掩码值本身也会暴露该字段存在。

### GWT-001 日志、指标与追踪统一

- GIVEN 平台运维、安全或审核角色具备有效身份，且父能力声明的输入与上游事实成立。
- WHEN 参与者执行“日志、指标与追踪统一”对应的公开行为。

- AND 失败时返回 canonical failure，且不产生伪成功事实。
