# L3 Story：日志、指标与追踪统一 (`log-metric-trace-unification`)

> 所属能力：[`observability-and-alerting`](../spec.md)

> Journey / Scenario：横切工程能力；由父 L2 spec 参与 AppRoot Journey。

> 设计归属：[L1 DEC-001](../../design.md#dec-001)

## 1. 用户价值

作为平台运维、安全或审核角色，
我希望以 requestId 和 traceId 关联日志、指标与追踪，同时限制标签基数并脱敏主体数据，
从而获得可审计且可回滚的平台治理结果。

## 3. 行为要求

<a id="req-001"></a>
### REQ-001 日志、指标与追踪统一

- 以 requestId 和 traceId 关联日志、指标与追踪，同时限制标签基数并脱敏主体数据。

<a id="req-002"></a>
### REQ-002 契约声明的指标名是逻辑 join key，不承诺存在同名时间序列

- operation 契约里的指标声明名是契约层逻辑标识，用于把契约事实与告警规则、看板和值班口径关联；它不承诺运行时注册了同名时间序列。
- 真实可查询的时间序列由运行时中间件统一注册，具备 SLO 所需的形状；绝大多数声明名在运行时没有对应序列，只作为规则标签值出现。
- 声明名只能出现在告警与看板的标签位置，不得出现在 PromQL 的序列名位置；出现在序列位置即为错误引用并被门禁阻断。
- 声明名可被同一族多个 operation 共享作为分组键，因此与 operation 全限定名不是一一对应，二者在同一条规则上并存是有意设计。
- 因为声明名由人工维护，重命名或拆分 operation 时必须同步复核其声明名归属，不得让分组键继续指向已消失的语义族。

<a id="req-003"></a>
### REQ-003 契约声明的 p95 延迟目标与指标名同裁决，并与入站超时预算成约束关系

- operation 契约里的 p95 延迟目标与指标声明名适用同一裁决，它是契约层逻辑标识，用于把契约事实关联到告警规则、看板与值班口径，不承诺运行时存在同名告警序列。
- 该延迟目标与同一 operation 的入站超时预算不是可以各自漂移的两个独立数值，二者关系由「超时预算不小于 p95 延迟目标」这一条约束表达。
- 违反该约束意味着契约在声明正常延迟就会触发超时，属于契约缺陷，必须修正契约声明而不是在运行时放宽预算。

## 5. 验收场景

<a id="gwt-001"></a>
### GWT-001 日志、指标与追踪统一

- GIVEN 平台运维、安全或审核角色具备有效身份，且父能力声明的输入与上游事实成立。
- WHEN 参与者执行“日志、指标与追踪统一”对应的公开行为。
- THEN 以 requestId 和 traceId 关联日志、指标与追踪，同时限制标签基数并脱敏主体数据。
- AND 失败时返回 canonical failure，且不产生伪成功事实。
