# L2 Design：消息可靠性地基 (`message-reliability-foundation`)

> 对应规格：[L2 spec](./spec.md)
>
> 设计触发原因：跨 App / realtime-gateway / chat-service / notification-service 四方状态与所有权变化，且涉及本地存储归属迁移与外部推送 provider 依赖。

## 1. 背景、目标与非目标

- 背景：可靠性缺口分散在 App、realtime-gateway、chat-service 与 notification-service 四方，任何一方单独修复都不成立。
- 背景事实：消息时间线只在内存中存在，磁盘上仅有服务于搜索的副本，传输恢复与缺口补齐的代码路径存在但无人发出事件也无人调用，断连期间的事件既无持久化也无推送兜底。
- 设计目标：确立「本地一份权威副本 + seq 单调 + 至少一次投递 + 端侧幂等」这一条闭合链路，并让链路上每一段都有可观察证据。
- 非目标：不改变会话来源建模与消息类型语义，不引入端到端加密，不改变成员治理。

## 2. Story 协作与状态流

- 状态 owner：服务端拥有 seq 与消息事实，端侧拥有本地副本与同步游标，notification-service 拥有投递记录终态。
- 并发边界：同一会话的本地写入串行化，实时插入、翻页补齐与补洞结果合并到同一条插入链路。
- 幂等边界：服务端以 `clientMsgId` 去重写入，端侧以 `id` 与 `clientMsgId` 双键去重展示。
- 一致性窗口：本地副本相对服务端最终一致，收敛依据是 seq；未收敛期间必须对用户表达为「同步中」而非「已完整」。

## 3. 端云与数据流

- App 责任：水合本地副本、维护同步游标、按最大 seq 请求补洞、对来源分流展示、上报运行时性能指标。
- Metadata/contract：长轮询请求与回执的游标字段、传输恢复事件类型、推送投递作业的路由与终态枚举，均只在所属服务 contracts 定义。
- Service/Data/Ops 责任：chat-service 保证 seq 原子分配与写入幂等，realtime-gateway 保证事件落持久流并支持按游标重放，notification-service 保证投递作业幂等与终态真实。
- 缓存或投影：本地时间线是缓存而非真相源，允许被清空并可从服务端完全重建。
- 外部依赖：APNs / FCM 作为最终投递通道，其不可用必须表达为投递未确认而不是投递失败即丢弃。

## 4. 关键决策

<a id="dec-001"></a>
### DEC-001 本地消息存储复用既有 chat 本地库，不新建第二个库

- 决策：把既有 chat 本地库提升为 canonical 本地消息存储，时间线与搜索共用同一份消息行。
- 理由：消息在端上只能有一份真相。两个库会立刻产生「搜索能搜到但时间线看不到」这类不可解释状态，且删除、撤回与清理需要双写。
- 被否决方案：为时间线新建独立存储并与搜索库异步对账——对账本身就是第二真相源的证据。
- 影响 Story：[`message-timeline-local-persistence`](./message-timeline-local-persistence/spec.md)、[`message-paging-and-ordering`](./message-paging-and-ordering/spec.md)
- 关联要求：`REQ-001`
- 关联验收：`SIT-001`

<a id="dec-002"></a>
### DEC-002 断连补洞以持久事件流加游标重放实现，不以全量重拉实现

- 决策：会话事件在广播之外额外落持久流，长轮询与重连携带游标并由服务端回执下一游标；端侧按已持有的最大 seq 补齐。
- 理由：全量重拉的代价随会话长度线性增长，且无法区分「服务端没有更多」与「本次拉取被截断」。游标重放让缺口补齐的完整性可判定。
- 被否决方案：重连后重新拉取最近 N 条——N 小则漏，N 大则在群会话上放大流量，且漏与不漏对端侧不可观察。
- 影响 Story：[`realtime-push-and-offline-sync`](./realtime-push-and-offline-sync/spec.md)
- 关联要求：`REQ-003`
- 关联验收：`SIT-002`

<a id="dec-003"></a>
### DEC-003 推送经 notification-service 投影，chat-service 不直连 provider

- 决策：chat 事件进入 notification-service 的幂等投影与投递作业，由既有 provider 边界完成实际下发。
- 理由：投递重试、端点失效回收、限频与终态审计已经在 notification-service 存在。让 chat 直连 provider 会复制一整套投递状态机，并产生第二份端点真相。
- 被否决方案：chat-service 直接调用 APNs/FCM——投递终态将无法与站内通知记录对账。
- 影响 Story：[`chat-offline-push-delivery`](./chat-offline-push-delivery/spec.md)
- 关联要求：`REQ-004`
- 关联验收：`SIT-003`

## 5. 失败与恢复

- 失败：本地副本损坏、持久流截断、推送 provider 不可用、补洞请求超时。
- 检测：本地副本自校验与 seq 连续性检查，持久流游标越界，provider 回执缺失超时，补洞请求返回 canonical failure。
- 可见结果：区分「离线只读」「同步中」「同步失败可重试」三种态，推送未确认不展示为已送达。
- 恢复：本地副本可整体丢弃并从服务端按游标重建，投递作业按既有退避重试，补洞失败保留游标以便下次继续。
- 禁止 fallback：不得以空列表冒充无消息，不得以本地通知冒充远端推送，不得在补洞失败后静默截断时间线。

## 6. 质量与观测

- 性能：会话首帧、长列表滚动 jank 比、发送到气泡确认延迟按声明预算约束，端侧指标复用既有 feed 性能观测的分子分母形状以保持干净分母。
- 容量：网关按连接数与订阅积压扩缩，而非仅按 CPU 与内存。
- 隐私：推送载荷不得携带消息正文以外的关系事实；离线投递记录不保留正文。
- 指标 / SLO：服务端阈值复用所属 `operations.yaml` 的 `slo.latency_p95_ms`，告警在既有 chat 与 realtime-gateway 规则组内扩展，不新建规则组。
- kill-switch：推送投递与持久流重放各自可独立关闭，关闭后降级为在线实时投递并对用户表达为「仅在线接收」。

## 7. 迁移与回滚

- 切换顺序：先建立本地副本与游标，再启用持久流与补洞，最后接入推送投递；每一步都可单独回滚而不影响前一步。
- 数据处理：本地副本为可重建缓存，回滚时清空即可，不产生数据迁移。
- 删除的实现：无人发出的传输恢复分支与无人调用的补洞入口在本能力落地时删除，不保留为兼容路径。
- 回滚条件：任一步骤导致消息重复或顺序回退时立即回滚该步骤，并保留已采集的 seq 连续性证据用于定位。
